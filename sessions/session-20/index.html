Capstone: CD to Cloud Kubernetes

Session 19 wired continuous deployment to a local Kubernetes cluster — kind or minikube, running on the same machine as everything else. Today the exact same GitHub Actions pipeline pattern gets retargeted at a real managed cloud cluster (AKS, GKE, or EKS — pick one), which means real authentication, a real public IP address, and real production stakes.

Estimated time: 40–50 minutes

Flow: Pre-quiz → Concept → Lab → Commit → Post-quiz

2. Pre-Coding Quiz

Answer before reading the concept. Need 4/5 to proceed.

Question 1 of 5

What does a managed cloud Kubernetes cluster (AKS/GKE/EKS) actually add compared to kind or minikube?

kubectl and the manifest format stay the same. What changes is that the cluster is real infrastructure you don't own, with authentication and a real public IP in play.
Question 2 of 5

What is kubeconfig, functionally?

kubeconfig bundles the cluster address with authentication material. Anyone holding a valid one can run kubectl against that cluster as that identity.
Question 3 of 5

Why does a pod need an imagePullSecret to run masker-server from a private Docker Hub repo?

Public images pull anonymously. A private repo requires the kubelet to authenticate first, and imagePullSecrets is how the pod spec supplies that credential.
Question 4 of 5

You run kubectl get svc masker-client -n masker-prod right after applying it. What should EXTERNAL-IP show?

A LoadBalancer Service asks the provider to provision real infrastructure, which takes time. <pending> is expected right after apply, not a failure.
Question 5 of 5

Why does the CD workflow encode kubeconfig as base64 before storing it as a GitHub secret?

Base64 is encoding, not encryption — the secret itself is what protects the value. Encoding just makes an arbitrary multi-line YAML blob safe to paste as one secret string, and the workflow decodes it back before use.

3. The Concept

What actually changes moving from local to cloud

Session 19's kind or minikube cluster ran on one machine, with no real authentication story and no real external network boundary — anything exposed was only ever reachable from that same machine. Every kubectl command and every manifest from that session still applies unchanged today. What's new is that the cluster now lives in a cloud provider's infrastructure, so getting kubectl pointed at it requires proving who you are, and exposing a Service to the outside world now means a real, routable public IP address.

Authenticating and fetching kubeconfig

Each cloud provider has its own CLI for logging in and its own command for writing cluster credentials into ~/.kube/config. The lab presents all three because the pattern is identical — pick whichever provider the cluster actually runs on: 

# Azure (AKS)
az login
az account set --subscription "<subscription-id>"
az aks get-credentials -g <resource-group> -n <aks-cluster-name>

# Google Cloud (GKE)
gcloud auth login
gcloud config set project <gcp-project-id>
gcloud container clusters get-credentials <gke-cluster-name> --region <region>

# AWS (EKS)
aws configure
eksctl utils write-kubeconfig --cluster <eks-cluster-name> --region <region>

# Verify, regardless of provider
kubectl config current-context
kubectl get nodes

Once kubectl get nodes lists real nodes, kubectl is fully authenticated to the cloud cluster — every command from this point on behaves exactly like it did against kind, just against different infrastructure.

Image pull secrets for a private registry

kubectl create namespace masker-prod

kubectl create secret docker-registry dockerhub-secret \
  --docker-server=https://index.docker.io/v1/ \
  --docker-username=$DOCKERHUB_USERNAME \
  --docker-password=$DOCKERHUB_TOKEN \
  -n masker-prod

kubectl get secrets -n masker-prod

The Deployment then references that secret name under imagePullSecrets, so the kubelet on whichever node schedules the pod can authenticate to Docker Hub before pulling masker-server or masker-client.

Deployment and Service manifests, with probes

k8s-cloud/masker-server-deploy.yaml deploys the API with both a readiness and a liveness probe against its health endpoint: 

apiVersion: apps/v1
kind: Deployment
metadata:
  name: masker-server
  namespace: masker-prod
spec:
  replicas: 2
  selector:
    matchLabels:
      app: masker-server
  template:
    metadata:
      labels:
        app: masker-server
    spec:
      imagePullSecrets:
        - name: dockerhub-secret
      containers:
        - name: server
          image: "${DOCKERHUB_USERNAME}/masker-server:latest"
          imagePullPolicy: Always
          ports:
            - containerPort: 8080
          readinessProbe:
            httpGet: { path: /health, port: 8080 }
            initialDelaySeconds: 5
            periodSeconds: 5
          livenessProbe:
            httpGet: { path: /health, port: 8080 }
            initialDelaySeconds: 10
            periodSeconds: 10
---
apiVersion: v1
kind: Service
metadata:
  name: masker-server
  namespace: masker-prod
spec:
  selector:
    app: masker-server
  ports:
    - port: 8080
      targetPort: 8080
  type: ClusterIP

readinessProbe decides whether a pod is added to (or removed from) the Service's routable endpoints — a pod that fails it simply stops receiving traffic until it passes again. livenessProbe is more drastic: repeated failures cause Kubernetes to kill and restart the container. The server's Service stays ClusterIP — internal only, since only the client needs to be reachable from outside.

LoadBalancer: the public-facing Service

apiVersion: v1
kind: Service
metadata:
  name: masker-client
  namespace: masker-prod
spec:
  selector:
    app: masker-client
  ports:
    - port: 80
      targetPort: 80
  type: LoadBalancer

Setting type: LoadBalancer tells the cloud provider's Kubernetes integration to provision a real external load balancer and point it at this Service. That provisioning takes real time — typically under a couple of minutes, but it is not instant.

The CD workflow: kubeconfig as a base64 GitHub secret

The workflow triggers off the successful completion of the build workflow, decodes the kubeconfig secret to a real file, then applies the manifests in k8s-cloud/: 

name: Deploy to Cloud Kubernetes

on:
  workflow_run:
    workflows: ["Build and Push Masker Images"]
    types: [completed]

permissions:
  contents: read

jobs:
  deploy:
    if: ${{ github.event.workflow_run.conclusion == 'success' }}
    runs-on: ubuntu-latest
    env:
      NAMESPACE: masker-prod
    steps:
      - uses: actions/checkout@v4

      - name: Write kubeconfig from secret
        shell: bash
        run: |
          mkdir -p "$HOME/.kube"
          echo "${KUBECONFIG_B64}" | base64 -d > "$HOME/.kube/config"
        env:
          KUBECONFIG_B64: ${{ secrets.KUBECONFIG_B64 }}

      - name: Ensure namespace exists
        run: kubectl get ns "$NAMESPACE" || kubectl create ns "$NAMESPACE"

      - name: Create or update Docker Hub pull secret
        run: |
          kubectl -n "$NAMESPACE" create secret docker-registry dockerhub-secret \
            --docker-server=https://index.docker.io/v1/ \
            --docker-username="$DOCKERHUB_USERNAME" \
            --docker-password="$DOCKERHUB_TOKEN" \
            --dry-run=client -o yaml | kubectl apply -f -
        env:
          DOCKERHUB_USERNAME: ${{ secrets.DOCKERHUB_USERNAME }}
          DOCKERHUB_TOKEN: ${{ secrets.DOCKERHUB_TOKEN }}

      - name: Apply manifests
        run: |
          kubectl -n "$NAMESPACE" apply -f k8s-cloud/
          kubectl -n "$NAMESPACE" rollout status deploy/masker-server --timeout=120s
          kubectl -n "$NAMESPACE" rollout status deploy/masker-client --timeout=120s

Encoding as base64 isn't encryption — it's just what makes a multi-line YAML file with arbitrary special characters safe to paste into a single-line GitHub secret value. The secret storage itself is what actually protects it; the deploy job's first step reverses the encoding to get a usable file back.

Where this evolves next: a long-lived kubeconfig sitting in a GitHub secret is a real credential with broad access, stored indefinitely. The safer production pattern replaces it with OIDC workload identity federation — GitHub issues a short-lived, per-run token that the cloud provider's IAM exchanges for scoped, temporary cluster access, so there is no standing credential to leak or rotate. Today's lab uses the kubeconfig-secret approach because it's simpler to stand up first; treat OIDC as the next hardening step, not something to skip permanently.

4. Lab

Lab objective: Authenticate to a chosen cloud provider's Kubernetes cluster, deploy the Text Masker app into it with a private-registry pull secret and health probes, expose it publicly, and wire GitHub Actions to redeploy automatically after a successful build.
1

Authenticate and fetch kubeconfig

Pick one provider (AKS, GKE, or EKS) and log in, then pull cluster credentials into ~/.kube/config using that provider's command from the Concept section above. Confirm with:

kubectl config current-context
kubectl get nodes
2

Create the namespace and pull secret

kubectl create namespace masker-prod

kubectl create secret docker-registry dockerhub-secret \
  --docker-server=https://index.docker.io/v1/ \
  --docker-username=$DOCKERHUB_USERNAME \
  --docker-password=$DOCKERHUB_TOKEN \
  -n masker-prod

Confirm it exists with kubectl get secrets -n masker-prod before moving on — a missing or misnamed pull secret is the most common reason pods sit in ImagePullBackOff later.

3

Apply the manifests in k8s-cloud/

Create k8s-cloud/masker-server-deploy.yaml, k8s-cloud/masker-client-deploy.yaml, and k8s-cloud/masker-client-service.yaml following the Concept section's manifests, then apply the whole folder:

kubectl apply -f k8s-cloud/
kubectl get pods -n masker-prod -w

Watch pods move from ContainerCreating to Running, and confirm READY shows both containers passing their readiness probe before continuing.

4

Predict, then observe: the external IP

Before running the next command, write down what you expect EXTERNAL-IP to show in the first few seconds after the client Service is applied — pending, an address, or an error.

kubectl get svc masker-client -n masker-prod -w

Watch it transition from <pending> to a real IP or hostname. Was your prediction right about how long the wait was? Once it resolves, open http://<external-ip>/ in a browser and confirm the Text Masker client loads.

5

Wire the CD workflow

Base64-encode the working kubeconfig and store it as a GitHub Actions secret named KUBECONFIG_B64:

cat ~/.kube/config | base64 -w0

Paste the output into a new repository secret. Then add .github/workflows/deploy_cloud.yml using the workflow from the Concept section, triggered by workflow_run off the existing build-and-push workflow. Push a small, harmless change that triggers the build workflow and confirm the deploy job runs automatically afterward, without a manual trigger.

6

Predict, then observe: a broken build

Before testing this, predict what happens to the deploy job if the build workflow fails. Push a change that intentionally breaks the build (a syntax error is enough), and confirm in the Actions tab that the deploy job never runs — workflow_run filtered to conclusion == 'success' is what enforces that gate. Revert the intentional break afterward.

8. Post-Coding Quiz

Question 1 of 5

masker-server's Service is type ClusterIP while masker-client's is type LoadBalancer. Why the difference?

The API only needs to be reached by the client inside the cluster, so ClusterIP (internal-only) is sufficient and keeps it off the public internet. The client is the public-facing piece, so it gets the LoadBalancer.
Question 2 of 5

A pod is stuck showing ImagePullBackOff after applying the manifests. What's the most likely cause given today's setup?

ImagePullBackOff specifically means the kubelet couldn't authenticate to pull the image, which points straight at the imagePullSecrets reference and the secret's contents.
Question 3 of 5

The deploy workflow triggers on workflow_run filtered to conclusion == 'success'. What happens if the build workflow fails?

The if condition on the job gates it entirely on a successful build conclusion — a failed build simply never triggers a deploy attempt.
Question 4 of 5

Why is a long-lived kubeconfig stored as a GitHub secret considered less safe than OIDC workload identity, even though both work?

OIDC exchanges a short-lived, per-run token for scoped temporary access, so there's no long-lived credential sitting in secrets storage waiting to be leaked or forgotten.

10. What Breaks If This Knowledge Is Missing?

  • Skip the image pull secret: Every pod sits in ImagePullBackOff forever, and the failure looks generic unless you already know to check imagePullSecrets first.
  • Skip the readiness probe: A pod that's still starting up gets traffic routed to it immediately, so real users hit connection errors during every rollout instead of the Service waiting for it to actually be ready.
  • Treat kubeconfig casually (commit it, share it in chat, leave it in a script): It's a working credential with full cluster access — leaking it is equivalent to leaking a cloud admin password, not a minor config mistake.
  • Skip the workflow_run success gate: A broken image build gets deployed straight to the public cluster, taking the real endpoint down for actual users instead of just failing quietly in CI.

11. What We Learned

Today you learned: how to authenticate to a managed cloud Kubernetes cluster and fetch a working kubeconfig, how an image pull secret authorizes pulling from a private Docker Hub registry, how readiness and liveness probes gate real traffic and restarts, how a LoadBalancer Service earns a real public IP, and how to wire GitHub Actions CD to that cluster using a base64-encoded kubeconfig secret chained off a successful build via workflow_run — plus why OIDC workload identity is the safer evolution beyond a standing kubeconfig secret.
