Layer 3 Session 06 Packaging & Infrastructure as Code

Packaging Applications with Helm

Session 05 closed out Layer 2 by proving you can manage config and secrets with raw kubectl apply manifests. That approach does not scale past a handful of files: every environment needs its own copy of every YAML file, hand-edited and easy to drift out of sync. Today you meet Helm, the package manager for Kubernetes, and rebuild that same workflow around versioned, reusable charts instead of loose YAML.

Estimated time: 45–55 minutes

2. Pre-Coding Quiz

Answer before reading the concept. Need 4/5 to proceed.

Question 1 of 5

What problem does Helm solve that raw kubectl apply -f does not?

Helm still ultimately produces Kubernetes manifests applied through the API server. What it adds is packaging, templating, versioned releases, and reusable configuration.
Question 2 of 5

In a Helm chart, where do the actual Kubernetes manifest templates live?

templates/ holds the YAML files with Go template placeholders like {{ .Values.replicaCount }}. Chart.yaml is metadata, values.yaml is configuration, charts/ holds dependency charts.
Question 3 of 5

You install a chart with both a custom -f myvalues.yaml and a CLI --set replicaCount=5. Which value wins for replicaCount if they disagree?

Helm's precedence order is chart defaults, then -f values files, then --set flags last — the flag always wins over a file.
Question 4 of 5

What does helm template ./mychart do?

helm template is a pure rendering step — it lets you review exactly what would be applied before running helm install or helm upgrade.
Question 5 of 5

After a bad helm upgrade, what does helm rollback my-app 2 do?

Helm keeps a revision history per release. Rollback re-applies a specific prior revision's rendered manifests to the cluster.

3. The Concept — Helm as a Package Manager for Kubernetes

Why raw manifests stop scaling

A Deployment, a Service, an Ingress, and a ConfigMap for one application is four files to keep in sync by hand. Multiply that across dev, staging, and production, and it becomes four files times three environments, each with slightly different replica counts, image tags, and hostnames — all edited manually, all easy to let drift apart. Helm exists to turn that pile of near-duplicate YAML into a single chart plus a small set of values per environment.

Anatomy of a chart

mychart/
  Chart.yaml          # name, version, appVersion — chart metadata
  values.yaml         # default configuration values
  templates/          # Kubernetes manifests with {{ .Values.x }} placeholders
    deployment.yaml
    service.yaml
    _helpers.tpl       # reusable template snippets (labels, names)
  charts/             # any dependency charts (subcharts) live here

Chart.yaml declares what the chart is: 

apiVersion: v2
name: mychart
description: A Helm chart for Kubernetes
type: application
version: 0.1.0        # chart version — bump this when the chart changes
appVersion: "1.16.0"   # the version of the app being deployed

values.yaml is the default configuration every template reads from: 

replicaCount: 1
image:
  repository: nginx
  pullPolicy: IfNotPresent
  tag: ""
service:
  type: ClusterIP
  port: 80

A template then references those values instead of hardcoding them: 

spec:
  replicas: {{ .Values.replicaCount }}
  template:
    spec:
      containers:
        - name: {{ .Chart.Name }}
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag | default .Chart.AppVersion }}"

Change replicaCount in one place, and every place that reads it updates consistently — that substitution is the entire value proposition of a chart over a folder of static YAML.

Installing from a repository

Most charts you use day to day are not ones you write — they are published by projects like Bitnami or the Kubernetes ingress-nginx maintainers. You add their repository once, then install by name: 

helm repo add bitnami https://charts.bitnami.com/bitnami
helm repo add ingress-nginx https://kubernetes.github.io/ingress-nginx
helm repo update

helm install my-redis bitnami/redis
helm list
helm uninstall my-redis

my-redis here is the release name — a specific, named instance of a chart running in the cluster. The same chart can be installed multiple times under different release names.

Values precedence: three layers, most specific wins

Every value a template reads comes from exactly one of three layers, resolved in this order — later layers override earlier ones: 

# 1. Chart defaults (values.yaml shipped with the chart) — lowest priority
# 2. A custom values file passed with -f              — overrides #1
# 3. --set key=value flags on the command line          — highest priority

helm install myapp ./mychart -f values.yaml --set replicaCount=3
# replicaCount ends up as 3, even if values.yaml said something else

Previewing before you deploy

helm template and helm lint both let you catch problems before a single manifest reaches the cluster: 

helm template myapp ./mychart -f values.yaml   # print rendered YAML, apply nothing
helm lint ./mychart                             # validate chart structure and syntax

Upgrade and rollback: a release has history

helm upgrade does not delete and recreate a release — it applies new values or a new chart version to the existing release in place, and records the change as a new numbered revision. 

helm upgrade my-redis bitnami/redis --set replica.replicaCount=2
helm list                     # shows the release, now at revision 2
helm rollback my-redis 1      # re-apply revision 1's manifests
helm list                     # back to the prior state

4. Lab

Lab objective: Install and remove a published chart, scaffold your own chart, override its values two ways, then practice upgrade and rollback on a real release.
1

Verify Helm and add repositories

helm version
helm repo add bitnami https://charts.bitnami.com/bitnami
helm repo add ingress-nginx https://kubernetes.github.io/ingress-nginx
helm repo update

Predict before running: what do you expect helm repo update to print if you have never added these repos before versus the second time you run it?

2

Install, list, and uninstall a published chart

helm install my-redis bitnami/redis
helm list
helm uninstall my-redis
helm list

Stop and think: after helm uninstall, does helm list show the release at all, or does it disappear entirely? Confirm before moving on.

3

Scaffold and deploy your own chart

helm create mychart
helm lint ./mychart
helm install myapp ./mychart

Open the generated mychart/values.yaml and mychart/templates/deployment.yaml. Find the exact line in the template that reads replicaCount from values.

4

Override values two ways and compare

# Method A — edit values.yaml, set replicaCount: 3, then:
helm upgrade myapp ./mychart -f mychart/values.yaml

# Method B — leave values.yaml alone, override on the CLI instead:
helm upgrade myapp ./mychart --set replicaCount=5

Predict before running: if both changes are applied one after another, how many replicas does the Deployment end up with after Method B runs? Run kubectl get deployment myapp-mychart -o jsonpath='{.spec.replicas}' to check.

5

Preview with helm template before your next change

helm template myapp ./mychart --set replicaCount=2 | less

Confirm the rendered replicas: line matches what you passed, then actually apply it with helm upgrade.

6

Upgrade and rollback

helm upgrade myapp ./mychart --set replicaCount=4
helm list                    # note the REVISION number
helm rollback myapp 1
helm list                    # confirm revision changed, replicaCount reverted

If your Helm install fails to authenticate against a registry — for example over an SSH session where a desktop credential helper is unavailable — the fix is almost always a file-based Docker/Helm registry config rather than anything about the chart itself. Clean up any stuck release name with helm uninstall before retrying an install under the same release name.

8. Post-Coding Quiz

Question 1 of 5

Your deployment.yaml template contains replicas: {{ .Values.replicaCount }}. If values.yaml has no replicaCount key at all and you install with no --set flag, what happens?

Templates only substitute what values actually provide. A missing key renders as empty, which is exactly why values.yaml should declare sane defaults for anything a template reads.
Question 2 of 5

You run helm install myapp ./mychart twice in a row using the same release name without uninstalling first. What happens?

Release names must be unique. Reusing one without an uninstall (or without switching to helm upgrade) produces a "name already in use" error.
Question 3 of 5

What is the difference between helm upgrade and running helm uninstall followed by helm install again?

Upgrade is a targeted, tracked change to an existing release. Uninstalling and reinstalling throws away that revision history and briefly removes the workload entirely.
Question 4 of 5

You want to confirm exactly what YAML a chart would produce with a specific set of overrides, without risking any change to the cluster. Which command do you reach for?

helm template renders locally with no cluster interaction at all, making it the safest way to inspect output before applying anything.

9. Reflection Questions

  1. Why does values precedence matter in practice — what real scenario would you use --set for instead of just editing values.yaml directly?
  2. What would go wrong on a team if two engineers both ran helm upgrade on the same release with different values, minutes apart, without checking helm list first?
  3. Why is helm rollback safer than manually trying to undo an upgrade by editing YAML and re-applying it yourself?

10. What Breaks If This Knowledge Is Missing?

  • Not understanding values precedence: a --set flag silently overrides a carefully maintained values.yaml, and the engineer has no idea why their file's change did not take effect.
  • Skipping helm lint or helm template before deploying: a typo in a template placeholder only surfaces as a broken Deployment in the cluster, instead of being caught locally in seconds.
  • Reusing a release name without uninstalling or upgrading: installs fail with confusing "name already in use" errors that look like a cluster problem but are actually a release-naming mistake.

11. What We Learned

Today you learned: a Helm chart packages Kubernetes manifests behind configurable values, releases have upgrade/rollback history instead of being replaced wholesale, and values precedence resolves in a fixed order from chart defaults to a values file to CLI --set flags.
