Layer 7 Session 19 Capstone: Ship a Real App

Capstone: CD to Local Kubernetes

Session 18 finished with a completed CI build automatically redeploying the Text Masker containers on plain local Docker — a workflow that worked, but that treats each container as a single, unmanaged process with no restart policy, no scaling story, and no clean way to watch a rollout in progress. Today the deployment target changes from raw docker run to a real, local Kubernetes cluster: a Deployment for each component, a Service that exposes them on a stable port, an image-pull secret so the cluster can authenticate to a private registry, and a rollout you can watch — and roll back — on command.

Estimated time: 45–55 minutes

Flow: Pre-quiz → Concept → Lab → Commit → Post-quiz

  2. 2/5Create an imagePullSecret and reference it from a Pod spec to authenticate to a private registry
  3. 3/5Distinguish a Deployment (the blueprint) from a Pod (a running instance it stamps out)
  4. 4/5Write a NodePort Service that exposes both Text Masker components on a stable port

2. Pre-Coding Quiz

Answer before reading the concept. Need 4/5 to proceed.

Question 1 of 5

What does a Kubernetes namespace primarily do?

A namespace is a logical boundary. Resources created inside it are grouped together and kept separate from resources in other namespaces on the same cluster.
Question 2 of 5

Why does a Deployment need an imagePullSecret when pulling from a private Docker Hub repository?

Without a docker-registry secret referenced in the pod spec, the cluster has no way to authenticate to a private registry, and the image pull fails.
Question 3 of 5

What is the core difference between a Deployment and a Pod?

The Deployment is the blueprint — image, replica count, labels. Pods are the actual running containers it creates and replaces to match that blueprint.
Question 4 of 5

What does a NodePort Service do?

A NodePort Service opens a consistent port on the cluster's node that routes to whichever healthy pods currently match its selector.
Question 5 of 5

What is kubectl rollout status waiting for?

rollout status blocks the terminal until the Deployment reports that all its replicas are updated, available, and ready — the point a rollout can be called complete.

3. The Concept — From docker run to a Managed Cluster

CD to Docker vs CD to Kubernetes

Session 18's deploy step amounted to stopping an old container and starting a new one with docker run. That works for a single machine with one process each, but it has no concept of desired replica counts, no built-in restart-with-backoff behavior, and no structured way to confirm a rollout actually finished. Kubernetes replaces that ad-hoc script with three durable objects — a Deployment per component, a Service in front of it, and a namespace that keeps the whole lab contained — plus a couple of commands that can prove a rollout succeeded instead of hoping it did.

Verifying a local cluster

Before deploying anything, confirm a cluster is actually reachable and that it has at least one node ready to schedule work: 

kubectl cluster-info
kubectl get nodes

Either command failing before any manifest is written means the problem is the cluster itself (Docker Desktop's Kubernetes not enabled, minikube not started), not anything in this lab's YAML.

Namespaces and image-pull secrets

Everything in this lab lives inside one namespace, created once: 

kubectl create namespace masker-lab

Because the Text Masker images are pushed to a private Docker Hub repository, the cluster also needs a way to authenticate when pulling them. A docker-registry secret packages a username and access token into a form the cluster can present to the registry: 

kubectl create secret docker-registry dockerhub-secret `
  --docker-username=$env:DOCKERHUB_USERNAME `
  --docker-password=$env:DOCKERHUB_TOKEN `
  --docker-server=https://index.docker.io/v1/ `
  -n masker-lab

That secret does nothing on its own — a Pod spec has to reference it by name under imagePullSecrets before the cluster will actually use it during a pull.

The Deployment and Service manifest

k8s/deployment-server.yaml defines one Deployment and one NodePort Service for the server component; deployment-client.yaml follows the same shape for the client: 

apiVersion: apps/v1
kind: Deployment
metadata:
  name: masker-server
  namespace: masker-lab
spec:
  replicas: 1
  selector:
    matchLabels:
      app: masker-server
  template:
    metadata:
      labels:
        app: masker-server
    spec:
      imagePullSecrets:
        - name: dockerhub-secret
      containers:
        - name: masker-server
          image: <your-dockerhub-username>/masker-server:latest
          ports:
            - containerPort: 8080
---
apiVersion: v1
kind: Service
metadata:
  name: masker-server
  namespace: masker-lab
spec:
  type: NodePort
  selector:
    app: masker-server
  ports:
    - port: 8080
      targetPort: 8080
      nodePort: 30081

Note where imagePullSecrets lives: inside the Pod template.spec, not at the top level of the Deployment or only in the namespace. That placement matters — it is discussed further in the post-quiz.

The deployment script — deploy_k8s.ps1

Applying manifests gets the objects created once. Rolling out a new image after every build is a repeatable job better handled by a small script than typed by hand each time: 

param(
  [string]$DockerUser,
  [string]$Namespace = 'masker-lab'
)

$ErrorActionPreference = 'Stop'

Write-Host 'Starting rollout for Masker components...'

kubectl set image deployment/masker-server masker-server=$DockerUser/masker-server:latest -n $Namespace
kubectl rollout status deployment/masker-server -n $Namespace

kubectl set image deployment/masker-client masker-client=$DockerUser/masker-client:latest -n $Namespace
kubectl rollout status deployment/masker-client -n $Namespace

Write-Host 'Rollout complete. Validating pods...'
kubectl get pods -n $Namespace

Each component gets its own set image followed immediately by its own rollout status — that pairing is what turns "I told Kubernetes to update" into "Kubernetes confirms the update finished," one component at a time.

The workflow — deploy_k8s.yml

A GitHub Actions workflow ties the deploy script to the CI build from Session 18, firing only after that build workflow reports success: 

name: Deploy to Local Kubernetes

on:
  workflow_run:
    workflows: ["Build and Push Masker Images"]
    types:
      - completed

jobs:
  deploy:
    runs-on: self-hosted
    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Deploy to Local Kubernetes
        run: |
          pwsh .\deploy_k8s.ps1 -DockerUser $env:DOCKERHUB_USERNAME
        env:
          DOCKERHUB_USERNAME: ${{ secrets.DOCKERHUB_USERNAME }}
          DOCKERHUB_TOKEN: ${{ secrets.DOCKERHUB_TOKEN }}

Two details are load-bearing here. First, workflow_run names the upstream CI workflow exactly, so this job only fires once that build has actually finished. Second, runs-on: self-hosted means this job runs on hardware that can reach the local cluster — a hosted GitHub runner has no route to a machine's local Docker Desktop or minikube instance.

The full pipeline, end to end

Put together: the CI workflow builds and pushes both images, that completion fires the workflow_run trigger, a self-hosted runner picks up the deploy job and runs deploy_k8s.ps1, that script issues kubectl set image and kubectl rollout status against the local cluster's masker-lab namespace, and the resulting server and client pods answer requests behind the NodePort Service at localhost:30080 in a browser.

4. Lab

Lab objective: Stand up the Text Masker app on a local Kubernetes cluster with a real Deployment, Service, and image-pull secret, then automate rollouts through a self-hosted GitHub Actions workflow triggered by the existing CI build.
1

kubectl cluster-info

Confirm at least one node shows Ready before continuing.

kubectl create namespace masker-lab

Write the manifests and apply them

Create k8s/deployment-server.yaml and k8s/deployment-client.yaml following the shape shown in Section 3, then apply the whole directory into the namespace:

kubectl apply -f .\k8s\ -n masker-lab
4

Verify everything came up

kubectl get all -n masker-lab
kubectl get svc -n masker-lab

You should see one Deployment, one running Pod, and one Service per component.

5

Create deploy_k8s.ps1

Write the deploy script shown in Section 3 — set image followed by rollout status for the server, then the same pair for the client, finishing with a get pods summary.

6

Create .github/workflows/deploy_k8s.yml

Write the workflow shown in Section 3, triggered by workflow_run on the CI build workflow, running on self-hosted, calling deploy_k8s.ps1.

7

Predict, then trigger, then observe

Before pushing anything: predict how many replicas kubectl rollout status will report for each component, and roughly how long the rollout will take. Then push a commit that fires the CI build, let workflow_run chain into the deploy job, and watch the Actions log to see whether your prediction held.

8

Smoke test

kubectl get pods -n masker-lab
kubectl port-forward svc/masker-client -n masker-lab 30080:80
start http://localhost:30080

Confirm the app loads in a browser through the forwarded port before considering the lab complete.

8. Post-Coding Quiz

Question 1 of 5

Why is imagePullSecrets placed inside the Pod template's spec, rather than only existing once at the namespace level?

Creating a secret in a namespace doesn't automatically wire it to every pod. Each pod spec that needs it must list it explicitly under imagePullSecrets, or the pull attempt has nothing to authenticate with.
Question 2 of 5

What happens if kubectl rollout status times out before every replica finishes updating?

A timeout means rollout status could not confirm every replica became ready in time. It reports failure rather than silently continuing, which is exactly the signal a CD script should surface.
Question 3 of 5

How do a namespace and a secret together isolate this lab's workloads?

The namespace keeps masker-lab's Deployments and Services separate from anything else on the cluster, while the secret scoped to that namespace controls which credentials pods inside it can use to pull images.
Question 4 of 5

What is the minimal CD loop this lab automates?

set image plus rollout status, repeated per component, is the entire deploy_k8s.ps1 script — a small, auditable loop rather than a full manifest reapply on every push.
Question 5 of 5

Session 20 will change this workflow by:

Session 20 keeps the Deployment, Service, and rollout mechanics from this session and retargets them at a cluster that lives in the cloud instead of on the local machine.

10. What Breaks If This Knowledge Is Missing?

  • Skip the imagePullSecret: Pods sit in ImagePullBackOff forever — the Deployment looks created, but nothing ever actually starts running.
  • Skip rollout status after set image: The script reports success the instant it fires the command, even if the new pods never actually become ready, hiding a broken deploy behind a green checkmark.
  • Confuse Deployment with Pod: Deleting a Pod by hand looks like a fix, but the Deployment just stamps out a replacement immediately — the underlying image or config problem is still there.

11. What We Learned

Today you learned: how a namespace and an imagePullSecret isolate and authenticate a workload, how a Deployment differs from the Pods it manages, how a NodePort Service exposes those Pods on a stable port, and how kubectl set image paired with rollout status forms a minimal, auditable CD loop chained onto CI through workflow_run.
