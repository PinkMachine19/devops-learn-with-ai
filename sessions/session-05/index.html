Layer 2 Session 05 Kubernetes

ConfigMaps and Secrets

Session 04 gave every workload an isolated, bounded slice of the cluster — a namespace with quotas that stop one team from starving another. But scoping where a workload runs says nothing about how it gets configured. Today we solve that: how do you get settings and credentials into a running pod without baking them into the container image or hardcoding them into a manifest that ends up in git? ConfigMaps and Secrets are the answer, and getting comfortable with both closes out Layer 2 — Kubernetes Basics — before we move into Helm, where these same objects get generated for you from templates.

Question 1 of 5

What is the main problem with hardcoding a database password directly into a pod's YAML manifest?

A hardcoded value sits in plain text in the manifest, which usually lives in git, CI logs, and anywhere the file is shared — none of which are designed to keep secrets safe.
Question 2 of 5

What kind of data is a ConfigMap intended for?

ConfigMaps hold plain configuration values that aren't sensitive — they're stored and displayed as plain text throughout the Kubernetes API.
Question 3 of 5

By default, how are values stored in a Kubernetes Secret protected?

Base64 is an encoding, not encryption — it's trivially reversible. Anyone with API access to the Secret can decode it in one command.
Question 4 of 5

Why might mounting a Secret as a file be safer than injecting it as an environment variable?

Environment variables are often dumped into crash reports, debug logs, or shown by tools that list a process's environment — a file sitting in a mounted directory is less likely to be captured that way.
Question 5 of 5

In a Helm chart, what typically supplies the actual values that fill in a ConfigMap template?

Helm templates reference placeholders like {{ .Values.config }}, and values.yaml is where those placeholders get their real values from at install or upgrade time.

3. The Concept — Getting Config Into a Pod Safely

Why hardcoding config is a problem

A container image is meant to be built once and run anywhere — dev, staging, production, a teammate's laptop. The moment you bake a setting like a database URL or a mode flag into that image, you lose that portability: changing the value means rebuilding and re-pushing the image. Put a credential directly into a pod manifest instead, and the problem gets worse, because that manifest usually ends up committed to git, attached to a CI log, or pasted into a chat message — none of which are safe places for a password to live.

ConfigMap: external, non-sensitive configuration

A ConfigMap is a Kubernetes object that holds configuration as key-value pairs, separate from any image or pod definition. You can create one from literal values on the command line, or from a file: 

kubectl create configmap app-config \
  --from-literal=MODE=debug \
  --from-literal=VERSION=1.0

That ConfigMap now exists as its own object in the cluster. Any pod can reference it by name, and updating the ConfigMap doesn't require touching the image at all.

Secret: sensitive data — and the base64 nuance

A Secret looks and behaves almost identically to a ConfigMap, but is meant to hold sensitive values like passwords, tokens, or connection strings: 

kubectl create secret generic db-creds \
  --from-literal=USER=demo \
  --from-literal=PASS=<db-password>

Here is the nuance that trips people up: by default, Kubernetes Secrets are only base64-encoded, not encrypted. Encoding is a reversible transformation for safely representing binary-ish data as text — it is not designed to keep data hidden from anyone. Anyone with API access to read the Secret object can decode it in a single command: 

kubectl get secret db-creds -o jsonpath='{.data.PASS}' | base64 -d

In other words, a Secret protects your credential from someone glancing at a YAML file, but it does not protect it from anyone who already has access to the cluster's API. Real production setups add another layer on top — encryption at rest for the cluster's etcd store, or an external secrets manager (like a cloud provider's secret store or Vault) that Kubernetes only references.

Two ways to consume a ConfigMap or Secret: env vars vs files

Once a ConfigMap or Secret exists, a pod can pull its values in two different ways.

Mounted as environment variables:

apiVersion: v1
kind: Pod
metadata:
  name: config-env-demo
spec:
  containers:
    - name: app
      image: busybox
      command: ["sh", "-c", "env && sleep 3600"]
      envFrom:
        - configMapRef:
            name: app-config
        - secretRef:
            name: db-creds

Mounted as a file volume (ConfigMap example — Secrets follow the same pattern with secret.secretName):

apiVersion: v1
kind: Pod
metadata:
  name: config-volume-demo
spec:
  containers:
    - name: app
      image: busybox
      command: ["sh", "-c", "sleep 3600"]
      volumeMounts:
        - name: config-volume
          mountPath: /etc/config
  volumes:
    - name: config-volume
      configMap:
        name: app-config

Secrets are generally better suited to a file mount for exactly the reason above: it keeps the sensitive value out of the environment variable list entirely.

Preview: Helm generates these from values.yaml

Writing a ConfigMap manifest by hand works fine for one pod, but gets repetitive across many services and environments. Helm charts solve this by templating the ConfigMap itself, with a values.yaml file supplying the real values: 

helm create configmap-demo
cat configmap-demo/templates/configmap.yaml

Inside that generated template you'll find placeholders like {{ .Values.config }} — Helm fills those in from values.yaml when you install or upgrade the chart, producing the exact same kind of ConfigMap object you created by hand in this lab, just generated instead of typed. That's the subject of Session 06.

4. Lab

Lab objective: Create a ConfigMap and a Secret, mount each of them into a pod two different ways — as environment variables and as a file volume — verify the values from inside the running pod, then take a short look at how Helm would generate a ConfigMap template before cleaning everything up.
1

Create a ConfigMap from literal values

kubectl create configmap app-config \
  --from-literal=MODE=debug \
  --from-literal=VERSION=1.0

Confirm it exists: kubectl get configmap app-config -o yaml. You should see MODE: debug and VERSION: "1.0" under data, in plain text.

2

Create a Secret for credentials

kubectl create secret generic db-creds \
  --from-literal=USER=demo \
  --from-literal=PASS=<db-password>

Replace <db-password> with a value of your own — never a real production password in a lab exercise. Then run kubectl get secret db-creds -o yaml and notice the value under data.PASS is a base64 string, not plain text.

3

Verify both resources exist

kubectl get configmaps,secrets

Both app-config and db-creds should appear in the output, alongside the default kubernetes.io/service-account-token secret Kubernetes creates automatically per namespace.

4

Write and apply a pod that mounts both as environment variables

Save this as k8s/config/pod-env.yaml:

apiVersion: v1
kind: Pod
metadata:
  name: config-env-demo
spec:
  containers:
    - name: app
      image: busybox
      command: ["sh", "-c", "sleep 3600"]
      envFrom:
        - configMapRef:
            name: app-config
        - secretRef:
            name: db-creds
kubectl apply -f k8s/config/pod-env.yaml
5

Predict, then observe: check the environment variables inside the pod

Before running the command below, predict: will the Secret's PASS value print in plain text, or still in base64 form, once it's an environment variable inside the container?

kubectl exec -it config-env-demo -- env | grep -E "MODE|VERSION|PASS"

You should see MODE=debug, VERSION=1.0, and PASS=<db-password> all in plain text. The base64 encoding only applies to how the Secret is stored in the Kubernetes API — once it's injected into a container, it arrives as the original decoded value. This is exactly why env vars are risky for Secrets: the moment something logs the environment, that plain-text value goes with it.

6

Write and apply a pod that mounts the ConfigMap as a file

Save this as k8s/config/pod-volume.yaml:

apiVersion: v1
kind: Pod
metadata:
  name: config-volume-demo
spec:
  containers:
    - name: app
      image: busybox
      command: ["sh", "-c", "sleep 3600"]
      volumeMounts:
        - name: config-volume
          mountPath: /etc/config
  volumes:
    - name: config-volume
      configMap:
        name: app-config
kubectl apply -f k8s/config/pod-volume.yaml
7

Exec in and read the mounted files

kubectl exec -it config-volume-demo -- ls /etc/config
kubectl exec -it config-volume-demo -- cat /etc/config/MODE

You should see MODE and VERSION listed as files, and cat /etc/config/MODE should print debug. Each key in the ConfigMap became its own file, with the value as the file's contents.

8

Preview: how Helm would generate this ConfigMap for you

helm create configmap-demo
cat configmap-demo/templates/configmap.yaml

Look for placeholders such as {{ .Values.config }} in the generated template, and the matching key under configmap-demo/values.yaml. This is only a look, not a full Helm lab — Session 06 covers packaging an application as a chart in depth. Once you've looked, delete the scaffolded chart directory: rm -rf configmap-demo.

9

Clean up

kubectl delete pod config-env-demo config-volume-demo
kubectl delete configmap app-config
kubectl delete secret db-creds

Confirm the cluster is clean with kubectl get pods,configmaps,secrets before moving on.

Which statement about Kubernetes Secrets is accurate by default?

This is the core nuance of the session: encoding is not encryption, and Secrets need extra measures like encryption at rest or an external secrets manager for real protection.

Both mechanisms work technically, but a value tucked into an environment variable is much more likely to be accidentally exposed by logging or debugging tools than one sitting in a file the app deliberately opens.

10. What Breaks If This Knowledge Is Missing?

  • Credentials get committed to git in plaintext YAML: without ConfigMaps and Secrets, developers hardcode values directly into manifests, and those manifests inevitably end up in version control history — often permanently, even after a later "fix" commit removes them.
  • Secrets accidentally get logged because they were only ever env vars: a Secret injected as an environment variable can leak into a crash dump, a debug log line, or a support ticket screenshot, without anyone intending it.
  • An image gets rebuilt just to change a config value: without a ConfigMap, updating something as simple as a feature flag or a log level means editing the Dockerfile, rebuilding, re-pushing, and redeploying — turning a one-line change into a full pipeline run.
  • A base64 string gets mistaken for "secure": a developer who doesn't know the encoding-versus-encryption distinction might treat a Secret as sufficient protection on its own, skipping encryption at rest or an external secrets manager that the situation actually calls for.

11. What We Learned

Today you learned: ConfigMaps store non-sensitive configuration outside an image, Secrets store sensitive values but are only base64-encoded by default (not encrypted), and both can be consumed as environment variables or mounted as files — with file mounts generally the safer choice for anything sensitive. This closes Layer 2 — Kubernetes Basics.
