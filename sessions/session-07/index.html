Answer before reading the concept. Need 4/5 to proceed.

Question 1 of 5

What is the correct order of Terraform's core workflow?

init prepares providers and backend, plan previews changes, apply makes them real, and destroy tears infrastructure back down when it's no longer needed.
Question 2 of 5

What is the Terraform state file for?

The state file is Terraform's record of real-world resources it manages. Every plan compares config, state, and (implicitly) reality to figure out what needs to change.
Question 3 of 5

Why does a private subnet need an explicit gateway resource in cloud Terraform configs?

In cloud providers, outbound and inbound internet access is not implicit — an internet gateway or NAT gateway is a distinct resource you have to declare.
Question 4 of 5

Which best describes what Terraform variables and outputs are for?

Variables parameterize a configuration (like a CIDR range or VM size); outputs surface computed results after apply, such as a resource's public IP address.
Question 5 of 5

Why does this lab end with terraform destroy rather than leaving the VM running?

Cleaning up provisioned infrastructure when a lab is done is a basic IaC habit — it's the same discipline that matters in real cloud accounts where idle resources cost money.

3. The Concept — Declarative Infrastructure with Terraform

Terraform provisions infrastructure, not applications

Helm packages what runs inside a Kubernetes cluster. Terraform is a layer below that: it provisions the network, the gateway, the compute, and — when needed — the cluster itself. The same declarative approach applies whether the target is a classic virtual machine or a managed Kubernetes service, and the same config can target AWS, Azure, GCP, or a local provider, because Terraform is cloud-agnostic by design.

The core workflow: init, plan, apply, destroy

terraform init      # download providers, prepare backend/state
terraform plan      # compare config vs current state, show what would change
terraform apply     # provision or update real infrastructure, update state
terraform destroy   # tear resources back down, update state

plan is the step that makes Terraform safe to use with confidence: it never changes anything by itself, it only computes and displays a diff between what your config says should exist and what the state file says currently exists.

State: the clipboard between config and reality

Terraform config is a blueprint. The state file is closer to a manager's clipboard — a running record of exactly which real resources Terraform created, and with what settings. Every plan or apply reads that state file first, so Terraform never has to guess what it already built. 

[ Config file ]  <-->  [ State file ]  <-->  [ Real infrastructure ]

This is also why the state file should never be hand-edited casually — it is the one source of truth Terraform trusts about what it owns.

Declaring a provider

Every Terraform config starts by declaring which providers it needs and configuring them. This example uses the Docker provider to simulate cloud-style resources locally, but the pattern is identical for AWS, Azure, or GCP — only the provider block and resource types change: 

terraform {
  required_providers {
    docker = {
      source  = "kreuzwerker/docker"
      version = "~> 3.0"
    }
  }
}

provider "docker" {}

Network, gateway, and a visible endpoint

Conceptually, provisioning a network follows the same shape everywhere: declare an address range, carve out a subnet inside it, attach a gateway so it can reach the outside world, then place a resource inside that subnet you can actually test. 

Terraform Network (VNet/VPC)
        +------------------+
        |  Virtual Network |
        |   (10.0.0.0/16)  |
        +------------------+
                 |
                 v
        +------------------+
        |      Subnet      |
        |   (10.0.1.0/24)  |
        +------------------+
[ Private Subnet ] -----> [ Gateway ] -----> [ Internet ]

Locally, this lab uses a Docker network and container instead of a cloud VNet and VM — your machine acts as the implicit gateway, so there is no separate gateway resource to declare. In a real cloud provider, that gateway is an explicit resource you write into the config, just like the network and subnet are. 

resource "docker_network" "labnet" {
  name = "phase4-net"
}

resource "docker_container" "web" {
  name  = "hello-web"
  image = "nginx:latest"

  networks_advanced {
    name = docker_network.labnet.name
  }

  ports {
    internal = 80    # nginx listens inside the container
    external = 8080  # reachable from your machine at this port
  }
}

output "web_url" {
  value = "http://localhost:8080"
}

docker_network.labnet.name is a reference to another resource's attribute — Terraform automatically figures out the network must be created before the container that depends on it, without you specifying that ordering explicitly.

Variables and outputs

Variables are a config's inputs; outputs are its results. Hardcoding a CIDR range or a container name works for a one-off lab, but the moment you need the same config for dev, staging, and prod, values like that belong in variables instead: 

variable "network_name" {
  description = "Name of the Docker network to create"
  type        = string
  default     = "phase4-net"
}

resource "docker_network" "labnet" {
  name = var.network_name
}

output "web_url" {
  value = "http://localhost:8080"
}

After terraform apply, outputs print to the terminal and remain queryable with terraform output — this is how you surface a resulting public IP, URL, or ID without digging through the state file by hand.

Legacy infrastructure and containerized infrastructure, side by side

Real enterprises are rarely all one or the other. A permanent VM running a database next to a fleet of short-lived containers is a normal hybrid setup, and Terraform is one of the few tools that manages both consistently — the same init → plan → apply → destroy loop applies whether the resource is a VM, a network, or eventually a Kubernetes cluster itself.

4. Lab

Lab objective: Provision a network and a small nginx endpoint with Terraform, verify it in a browser, then destroy everything cleanly.
1

Install and verify Terraform

terraform version

Confirm a version prints before continuing.

2

Create a working directory and declare the provider

mkdir terraform-lab && cd terraform-lab
# main.tf
terraform {
  required_providers {
    docker = {
      source  = "kreuzwerker/docker"
      version = "~> 3.0"
    }
  }
}

provider "docker" {}
terraform init

Predict before running: what do you expect terraform init to download or create in this folder? Check the new .terraform/ directory afterward.

3

Declare the network, container, and output

# append to main.tf
resource "docker_network" "labnet" {
  name = "phase4-net"
}

resource "docker_container" "web" {
  name  = "hello-web"
  image = "nginx:latest"

  networks_advanced {
    name = docker_network.labnet.name
  }

  ports {
    internal = 80
    external = 8080
  }
}

output "web_url" {
  value = "http://localhost:8080"
}
4

Plan, then apply

terraform plan
terraform apply

Stop and think: before typing "yes" at the apply prompt, count how many resources the plan says it will add. Does that match what you declared?

5

Test the endpoint externally

terraform output web_url

Open the printed URL in a browser and confirm the nginx welcome page loads.

6

Change a value and observe the plan

Change the external port from 8080 to 8081 and run terraform plan again.

Predict before running: will Terraform update the container in place, or does it need to destroy and recreate it? Read the plan output's action symbols to find out.

7

Clean up

terraform destroy

Confirm the container and network are both gone with docker ps and docker network ls afterward.

8. Post-Coding Quiz

Question 1 of 5

You changed a container's exposed port and terraform plan showed it would be destroyed and recreated instead of updated in place. Why might that happen?

Certain resource attributes are immutable after creation for a given provider/resource type — changing them forces Terraform to destroy and recreate rather than update.
Question 2 of 5

What does docker_network.labnet.name reference inside the docker_container block actually do?

Referencing another resource's attribute is how Terraform infers dependency order automatically, without an explicit depends_on being written.
Question 3 of 5

Why declare network_name as a variable instead of hardcoding "phase4-net" directly in the resource block?

Variables are exactly what makes one configuration reusable for dev, staging, and prod, instead of maintaining near-duplicate files that only differ by a name or size.
Question 4 of 5

If you skip terraform destroy after this lab and just delete the main.tf file, what happens to the running container?

Terraform only acts on infrastructure when you run plan/apply/destroy. Deleting a .tf file does nothing to already-provisioned resources — that's exactly why explicit destroy matters.

10. What Breaks If This Knowledge Is Missing?

  • Skipping terraform plan before apply: a config change gets applied blind, with no chance to catch an unexpected destroy-and-recreate before it happens to a resource that matters.
  • Hand-editing the state file: Terraform's record of reality drifts from what it actually manages, causing future plans to propose incorrect or destructive changes.
  • Forgetting terraform destroy on throwaway labs: resources keep running (and in a real cloud account, keep costing money) long after anyone is using them.
