Capstone: Blue-Green Deployment for the Real App

Session 20 got the Text Masker app running on a real managed cloud cluster with a public IP — but every deploy so far has been a straight rolling update, which means a bad release is visible to real users while pods cycle out one at a time. Today the blue-green pattern from Session 11 gets applied for real: two live environments, one switch, instant rollback.

Estimated time: 40–50 minutes

2. Pre-Coding Quiz

Answer before reading the concept. Need 4/5 to proceed.

Question 1 of 5

In a blue-green deployment, what is true about the "inactive" color at any given moment?

Both colors run as complete, live Deployments the whole time. The only difference is whether the Service selector currently points traffic at them.
Question 2 of 5

What actually decides which color receives live traffic?

A Service routes to any pod whose labels match its selector. Changing the selector's color value is the entire cutover mechanism.
Question 3 of 5

Why is blue-green's rollback faster than a rolling-update rollback?

Because the previous color's pods are still running, undoing a bad cutover needs no rebuild or redeploy — just patching the selector back.
Question 4 of 5

How does a rolling update differ from blue-green in terms of user exposure to a bad release?

A rolling update replaces pods gradually, so some requests hit old code and some hit new code during the swap. Blue-green has no such mixed-version window.
Question 5 of 5

Before flipping the Service selector to green, what should happen first?

Warming up and checking green while it's still isolated from live traffic is what makes the eventual cutover safe.

3. The Concept — Blue-Green, For Real This Time

Recap: what Session 11 taught in the abstract

Session 11 introduced blue-green deployment as a pattern: run two identical environments, send traffic to only one, and switch by flipping a single pointer instead of gradually replacing pods. That was taught with diagrams and a toy example. Today the same pattern gets applied to the Text Masker app that has been built, containerized, and deployed across Sessions 16 through 20 — with real Deployments, a real Service, and a real cutover.

Two Deployments, one label apart

Blue and green are not two different apps — they are two copies of the exact same Deployment spec, distinguished only by a color label. Each color gets its own masker-server and masker-client Deployment: 

apiVersion: apps/v1
kind: Deployment
metadata:
  name: masker-client-blue
  namespace: masker-bluegreen
  labels: { app: masker-client, color: blue }
spec:
  replicas: 2
  selector: { matchLabels: { app: masker-client, color: blue } }
  template:
    metadata: { labels: { app: masker-client, color: blue } }
    spec:
      containers:
      - name: client
        image: "${DOCKERHUB_USERNAME}/masker-client:latest"
        ports: [{ containerPort: 80 }]
        readinessProbe: { httpGet: { path: /, port: 80 }, initialDelaySeconds: 3, periodSeconds: 5 }

The green Deployment is identical except every color: blue becomes color: green. Both can run at full replica count simultaneously — running two colors at once is the whole point, not a transient state to rush through.

The Service selector is the single point of control

apiVersion: v1
kind: Service
metadata:
  name: masker-client
  namespace: masker-bluegreen
spec:
  selector:
    app: masker-client
    color: blue          # <- this line decides who gets traffic
  ports:
  - port: 30080
    targetPort: 80
  type: NodePort

A Kubernetes Service never talks to a Deployment directly — it watches for any pod whose labels match its selector and load balances across whichever pods currently qualify. With both colors running, the only thing distinguishing "live" from "idle" is which value sits in that color field.

Flipping traffic with kubectl patch

# point Service at blue (initial state)
kubectl -n masker-bluegreen patch svc masker-client --type='merge' \
  -p '{"spec":{"selector":{"app":"masker-client","color":"blue"}}}'

# verify which pods are currently receiving traffic
kubectl -n masker-bluegreen get endpoints masker-client -o yaml

# cut over to green
kubectl -n masker-bluegreen patch svc masker-client --type='merge' \
  -p '{"spec":{"selector":{"app":"masker-client","color":"green"}}}'

# verify again — the endpoint IPs should now belong to green pods
kubectl -n masker-bluegreen get endpoints masker-client -o yaml

kubectl get endpoints is the way to confirm a flip actually happened — it lists the real pod IPs currently backing the Service, which change the instant the selector's color value changes.

Ingress: routing that never has to change

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: masker-ingress
  namespace: masker-bluegreen
spec:
  rules:
  - host: masker.example.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: masker-client
            port:
              number: 30080

The Ingress rule points at the masker-client Service by name, never at a color directly. That's deliberate: since the Service already hides which color is active behind a stable name, the Ingress config — and the public hostname users hit — never needs to change during a cutover or a rollback.

The cutover procedure, end to end

Putting it together, a real cutover follows a fixed order: deploy green alongside the still-live blue, verify green independently (a port-forward and a manual request, or trusting its readiness probes), flip the Service selector to green, watch traffic and error rates for a few minutes, and then either leave blue running as a rollback target or scale it down once confidence is high. Rollback, if needed, is simply flipping the selector back to blue — no rebuild, no redeploy, no waiting for pods to terminate and restart.

How this differs from Session 20's rolling update

Every deploy through Session 20 used Kubernetes' default rolling update strategy: old pods terminate and new pods start up gradually, a few at a time. During that window, some requests are served by the old version and some by the new one — a real, if usually brief, exposure window for any bug in the new release. Blue-green removes that window entirely: the cutover is a single selector change, so every request before the flip goes to one full version and every request after goes to the other, with nothing in between.

4. Lab

Lab objective: Stand up blue and green Deployments of the Text Masker app in a dedicated namespace, verify green independently, cut traffic over with a Service selector patch, and then prove rollback works by flipping back.
1

Create the namespace

kubectl create namespace masker-bluegreen
kubectl label namespace masker-bluegreen purpose=release-strategy --overwrite

Confirm kubectl version --client and kubectl get nodes both work before starting, so any later failure is about the manifests, not the cluster connection.

2

Apply blue and green Deployments, plus the Service

kubectl apply -n masker-bluegreen -f .\k8s-bluegreen\masker-server-blue.yaml
kubectl apply -n masker-bluegreen -f .\k8s-bluegreen\masker-server-green.yaml
kubectl apply -n masker-bluegreen -f .\k8s-bluegreen\masker-client-service.yaml
kubectl get deploy,svc -n masker-bluegreen

Before running it: predict how many Deployments kubectl get deploy will list. There are two colors and two components (server, client) — write down the number, then check it against the actual output.

3

Verify green in isolation, before it takes traffic

With the Service still pointed at blue, port-forward directly to a green pod and confirm it responds:

kubectl -n masker-bluegreen get pods -l app=masker-client,color=green
kubectl -n masker-bluegreen port-forward deploy/masker-client-green 8081:80

Load http://localhost:8081 and confirm the app loads correctly. This step deliberately bypasses the Service, so a broken green never reaches real traffic.

4

Predict, then flip: patch the Service selector to green

Before running the command below, write down what you expect to happen to live traffic the instant the patch applies — does it happen gradually, like a rolling update, or all at once?

kubectl -n masker-bluegreen patch svc masker-client --type='merge' \
  -p '{"spec":{"selector":{"app":"masker-client","color":"green"}}}'

kubectl -n masker-bluegreen get endpoints masker-client -o yaml

Check the endpoint IPs in the output against kubectl get pods -l color=green -o wide. They should match exactly, confirming every request now lands on green pods.

5

Predict, then roll back: flip the selector to blue again

Before running this, predict how long the rollback will take compared to the original green rollout in step 2.

kubectl -n masker-bluegreen patch svc masker-client --type='merge' \
  -p '{"spec":{"selector":{"app":"masker-client","color":"blue"}}}'

kubectl -n masker-bluegreen get endpoints masker-client -o yaml

Because blue's pods never stopped running, this should complete immediately — no waiting for pods to start, no readiness delay. That instant reversal is the entire payoff of the pattern.

6

Optional: apply the Ingress route

kubectl apply -n masker-bluegreen -f .\k8s-bluegreen\masker-ingress.yaml
kubectl -n masker-bluegreen get ingress

If an ingress controller is installed on the cluster, this exposes the app through a stable hostname regardless of which color is currently live — confirming the Ingress config needs zero changes across a cutover.

8. Post-Coding Quiz

Question 1 of 5

After patching the Service selector from blue to green, what confirms the cutover actually happened?

A successful patch only means the Service object changed. Checking endpoints confirms which pod IPs are actually receiving traffic right now.
Question 2 of 5

Why does the blue Deployment stay running even after traffic has fully cut over to green?

Keeping blue's pods alive is what makes rollback instant. Scaling it down is a later, deliberate step once confidence in green is high, not a required cleanup.
Question 3 of 5

The Ingress rule for masker-client points at the Service name, not at a color. What does this buy?

Because the Service already hides which color is active, the Ingress config and the public hostname stay untouched through every cutover and rollback.
Question 4 of 5

How does a rolling update's exposure window differ from blue-green's?

A rolling update replaces pods a few at a time, so some requests hit each version during the swap. Blue-green has no such window — the selector change is atomic.

9. Reflection Questions

  1. Before flipping the selector to green, did you correctly predict that the cutover would be immediate rather than gradual? What made you expect that?
  2. Why does verifying green through a port-forward, before the flip, matter more here than it would with a rolling update?
  3. What would go wrong if the blue and green Deployments' pod template labels were identical instead of differing by color?

10. What Breaks If This Knowledge Is Missing?

  • Both Deployments use the same labels: The Service selector can no longer distinguish blue from green, so it load balances across both colors at once — exactly the mixed-version exposure blue-green exists to prevent.
  • Green is never verified before the flip: A broken green release goes straight to every user the instant the selector changes, with no isolated check to have caught it first.
  • Blue is deleted immediately after cutover: Rollback stops being instant — a bad green now requires waiting for blue to redeploy from scratch, which is exactly the slow rollback blue-green was meant to avoid.
  • The Ingress is left pointed at a color instead of the Service: Every cutover now requires an Ingress change too, reintroducing a coordination step the pattern is designed to remove.

11. What We Learned

Today you learned: blue-green keeps two full, live environments running behind a single Service, the Service selector's color label is the entire cutover mechanism, verifying the new color before flipping keeps a bad release from ever reaching users, and rollback is instant because the old color's pods never stopped running.
