Capstone: Canary Deployment for the Real App

Session 21 gave the Text Masker pipeline instant all-or-nothing rollback through a blue-green swap — but a full cutover still means every user hits the new version the moment the switch flips. Today the canary pattern from Session 13 stops being a diagram and becomes real: a small slice of live traffic tests a release before it ever reaches everyone else, running against the same masker-client image this course has been shipping since Session 16.

Estimated time: 40–50 minutes

  3. 3/5Observe a canary's behavior — logs and request counts — before deciding whether to trust it with more traffic

2. Pre-Coding Quiz

Answer before reading the concept. Need 4/5 to proceed.

Question 1 of 5

In a canary deployment, what is running at the same time as the stable version?

Canary means the new version is live and receiving real, if limited, production traffic alongside the version already in service.
Question 2 of 5

Where does the canary-weight percentage actually get configured for this lab?

nginx.ingress.kubernetes.io/canary-weight is set directly on the Ingress object, letting the Ingress controller split traffic without touching the app itself.
Question 3 of 5

Why watch the canary before increasing its traffic weight?

The entire point of limiting canary traffic is to give a human (or a metric) a window to notice problems before everyone is exposed to them.
Question 4 of 5

The canary is misbehaving. What is the fastest way to stop it from receiving new traffic?

Rollback here is a weight change or a scale-down — stable was never touched and keeps serving the rest of the traffic throughout.
Question 5 of 5

Compared to the blue-green pattern from Session 21, what does canary trade away?

Blue-green flips every user at once with one switch. Canary spreads that exposure out gradually, at the cost of extra steps and a longer promotion process.

3. The Concept

Canary, revisited from Session 13, now applied for real

Session 13 introduced canary deployments conceptually: send a small percentage of traffic to a new version, watch it, and only then decide whether to trust it with the rest. Today that idea gets wired directly into the Text Masker pipeline built across Sessions 16 through 21 — the same masker-client image, but running as two tracks at once instead of one.

Two Deployments, two Services, one Ingress

A stable track runs the version already trusted in production, sized for the bulk of traffic. A canary track runs the candidate version, sized small on purpose — often a single replica is enough to prove whether it behaves correctly under real requests. 

# masker-stable.yaml (excerpt)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: masker-stable
  namespace: masker-canary
  labels: { app: masker-client, track: stable }
spec:
  replicas: 2
  selector: { matchLabels: { app: masker-client, track: stable } }
  template:
    metadata: { labels: { app: masker-client, track: stable } }
    spec:
      containers:
      - name: client
        image: "${DOCKERHUB_USERNAME}/masker-client:latest"
        ports: [{ containerPort: 80 }]
---
apiVersion: v1
kind: Service
metadata:
  name: masker-stable
  namespace: masker-canary
spec:
  selector: { app: masker-client, track: stable }
  ports: [{ port: 80, targetPort: 80 }]

The canary Deployment and Service mirror this shape exactly, differing only in the track: canary label and a lower replica count: 

# masker-canary.yaml (excerpt)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: masker-canary
  namespace: masker-canary
  labels: { app: masker-client, track: canary }
spec:
  replicas: 1
  selector: { matchLabels: { app: masker-client, track: canary } }
  template:
    metadata: { labels: { app: masker-client, track: canary } }
    spec:
      containers:
      - name: client
        image: "${DOCKERHUB_USERNAME}/masker-client:latest"
        ports: [{ containerPort: 80 }]

Traffic splitting through Ingress annotations

With ingress-nginx installed, one Ingress object can point at both Services and carry canary annotations that tell the controller how to split incoming requests between them: 

# masker-ingress-canary.yaml (excerpt)
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: masker
  namespace: masker-canary
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
    nginx.ingress.kubernetes.io/canary: "true"
    nginx.ingress.kubernetes.io/canary-weight: "5"
spec:
  ingressClassName: nginx
  rules:
  - host: masker.canary.localtest.me
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service: { name: masker-stable, port: { number: 80 } }
      - path: /
        pathType: Prefix
        backend:
          service: { name: masker-canary, port: { number: 80 } }

With canary-weight: "5", roughly 5% of requests to masker.canary.localtest.me land on the canary Service and the rest land on stable. The traffic split happens at the Ingress controller layer — the application itself has no idea it is being canaried.

Promotion is a series of small, observable steps

# Set to 5%
kubectl -n masker-canary annotate ingress masker --overwrite `
  nginx.ingress.kubernetes.io/canary-weight="5"

# Watch canary pod logs / request counts, then increase to 50%
kubectl -n masker-canary annotate ingress masker --overwrite `
  nginx.ingress.kubernetes.io/canary-weight="50"

# Once confident, promote to 100% (or disable the canary flag)
kubectl -n masker-canary annotate ingress masker --overwrite `
  nginx.ingress.kubernetes.io/canary="false"

Each step raises the weight only after the previous step looked healthy. Promotion is never a single switch — it is a sequence of small, reversible increases, each one an opportunity to stop.

Rolling back a bad canary

If error rates rise or logs look wrong at any weight, the response is the same regardless of which step triggered it: annotate the weight back down to "0", or scale the canary Deployment to zero replicas with kubectl scale deploy/masker-canary --replicas=0. Stable was never interrupted, so the rollback is invisible to the large majority of users who were never routed to canary in the first place.

Canary versus blue-green

They solve related problems differently. Blue-green (Session 21) keeps two full environments ready and flips all traffic at once — simple to reason about, and rollback is just flipping back. Canary keeps both environments live simultaneously and exposes only a slice of traffic to the new version — slower to fully promote, but a bad release only ever affects a fraction of real users instead of all of them.

4. Lab

Lab objective: Stand up masker-stable and masker-canary side by side behind one canary-aware Ingress, send test traffic through it, ramp the canary weight up, and practice a rollback.
1

Confirm the cluster and ingress-nginx are ready

kubectl version --client
kubectl get nodes
kubectl get ns ingress-nginx

If ingress-nginx is missing, install it with Helm before continuing:

helm repo add ingress-nginx https://kubernetes.github.io/ingress-nginx
helm repo update
helm upgrade --install ingress-nginx ingress-nginx/ingress-nginx `
  --namespace ingress-nginx --create-namespace
kubectl -n ingress-nginx get pods
2

Apply the stable, canary, and Ingress manifests

kubectl create namespace masker-canary
kubectl apply -n masker-canary -f .\k8s-canary\masker-stable.yaml
kubectl apply -n masker-canary -f .\k8s-canary\masker-canary.yaml
kubectl apply -n masker-canary -f .\k8s-canary\masker-ingress-canary.yaml
kubectl get deploy,svc,ingress -n masker-canary

Before sending any traffic: predict roughly what fraction of requests will hit the canary pod, given the weight in masker-ingress-canary.yaml. Write the number down.

3

Send a burst of test traffic and count

Send a batch of requests against the Ingress host and tally which track answered each one (the response body or a per-track log line works for this). Compare the observed split against your prediction from Step 2 — at low weights and small sample sizes, expect the observed percentage to wander noticeably around the configured weight.

1..40 | ForEach-Object {
  curl.exe -s -o NUL -w "%{http_code}`n" http://masker.canary.localtest.me/
}
4

Ramp the canary weight and re-observe

# 5% -> 50%
kubectl -n masker-canary annotate ingress masker --overwrite `
  nginx.ingress.kubernetes.io/canary-weight="50"

Before repeating the traffic burst from Step 3: predict how the split should shift now that the weight is higher. Then repeat the burst and confirm the canary's share of responses rose accordingly.

5

Promote to 100%

kubectl -n masker-canary annotate ingress masker --overwrite `
  nginx.ingress.kubernetes.io/canary="false"

With the canary annotation disabled, all traffic returns to the single remaining rule (stable). At this point the canary version — once trusted — would typically be promoted to be the new stable Deployment, and the old stable retired.

6

Practice a rollback, then clean up

Re-enable the canary at a low weight, then simulate catching a problem: scale the canary Deployment to zero and confirm no traffic reaches it.

kubectl -n masker-canary scale deployment masker-canary --replicas=0
kubectl -n masker-canary get pods -l track=canary

When finished, tear the namespace down:

kubectl delete namespace masker-canary

7. Code Review Checklist

8. Post-Coding Quiz

Question 1 of 5

What does the canary Deployment's low replica count (often just 1) accomplish?

A small canary limits how many requests it can even serve, reinforcing the traffic-weight limit and keeping the blast radius of a bad release small.
Question 2 of 5

After setting canary-weight to "50" and sending 40 test requests, exactly 20 hit canary and 20 hit stable. Is this guaranteed every time?

canary-weight sets a probability per request, not a strict round-robin count — larger sample sizes converge toward the configured percentage, but small bursts can drift from it.
Question 3 of 5

Why promote in ramped steps (5% → 50% → 100%) instead of jumping straight to 100%?

The entire value of a canary comes from pausing at each step to observe — skipping straight to 100% defeats the purpose and behaves like blue-green without its instant rollback.
Question 4 of 5

The canary at 50% weight starts returning errors. What happens to users routed to stable during the rollback?

Rollback only touches the canary weight or replica count. Stable's Deployment and Service are never modified, so users routed there are unaffected.
Question 5 of 5

Which statement best compares canary and blue-green as covered in this course?

Blue-green (Session 21) trades gradual exposure for a simpler, instant, fully reversible switch. Canary (today) trades that simplicity for a smaller blast radius during rollout.

10. What Breaks If This Knowledge Is Missing?

  • No traffic weighting, deploy straight to 100%: Every user hits an unproven release simultaneously — a bad build affects the entire user base at once, with no early-warning slice to catch it first.
  • Canary deployed but never observed: The pattern becomes theater. Without watching logs or error rates at each weight, a broken canary can sit there being promoted anyway, and the whole point of limiting exposure is lost.
  • No rollback path (no weight-to-zero or scale-to-zero step): A bad canary either has to be fixed forward under pressure, or the whole namespace gets torn down — losing the fast, low-drama recovery a canary is supposed to provide.
  • Stable and canary sharing one Deployment instead of two: There is no way to run two versions concurrently at all, which removes the ability to canary anything in the first place.

11. What We Learned

Today you learned: canary deployments run a stable track and a small canary track side by side, split real traffic between them using Ingress-level weighting, watch the canary before trusting it further, promote it in small ramped steps, and roll it back cheaply by dropping its weight or replica count to zero — all without ever touching the stable track serving everyone else.

This is also the last new pattern in the course. Session 1 started with a single container running locally. Since then this course has moved through Kubernetes fundamentals, Helm and Terraform, Ingress and TLS, release strategies including blue-green and now canary, and the observability needed to trust any of it — and applied every one of those pieces, in order, to one real application: the Text Masker, built from Session 16 onward and shipped end to end, from a laptop to a real cluster, with the same deployment patterns used in production systems. That is the actual capstone — not a new concept today, but proof that the last 21 sessions add up to something that genuinely runs.
