Layer 1 Session 02 Docker Foundations — Gate

Multi-Container Apps with Docker Compose (PHP + MySQL)

Session 01 ran one container at a time by hand — a manual docker network create, a manual -v, a manual --network flag repeated on every command. That already got tedious with just two containers. Today you build a real two-service application, a PHP page backed by a MySQL database, first by wiring it up manually to feel the pain, then by collapsing the entire setup into one docker-compose.yml file and a single command. This session is the gate for Layer 1: everything from here on assumes multi-container thinking is second nature.

Estimated time: 85–95 minutes

1. Learning Objectives

  1. 1/5Explain why manually running multiple related containers is error-prone and hard to reproduce
  2. 2/5Write a docker-compose.yml describing a PHP service and a MySQL service, with volumes and environment variables
  3. 3/5Build a custom PHP image with the pdo_mysql driver so it can talk to MySQL
  4. 4/5Bring up the whole stack with docker compose up and understand the network Compose creates automatically
  5. 5/5Verify a full request path end to end: browser → PHP → MySQL → back to the browser

2. Pre-Coding Quiz

Answer before reading the concept. Need 4/5 to proceed.

Question 1 of 5

What problem does Docker Compose primarily solve?

Compose turns the sequence of docker run / docker network create / docker volume create commands from Session 01 into one declarative YAML file and one command.
Question 2 of 5

In a docker-compose.yml with services named web and db, how does the web service typically reach the db service?

Compose creates a project network and joins every service to it, and each service's name in the YAML file becomes its hostname on that network.
Question 3 of 5

Why does a plain php:apache image fail to connect to MySQL out of the box?

The base php:apache image doesn't include MySQL drivers. A Dockerfile has to install pdo_mysql before index.php's PDO connection can succeed.
Question 4 of 5

You run docker compose up -d. What does the -d flag do here, consistent with Session 01's usage of the same flag?

-d means detached, the same meaning it had for a single docker run in Session 01 — the containers keep running after the command returns your terminal.
Question 5 of 5

Every container in your stack shows "Up" in docker compose ps. Is the application definitely working correctly?

A container being "Up" just means its process hasn't exited. It doesn't confirm PHP can actually query MySQL and render a correct page — that requires an end-to-end check.

3. The Concept — From Manual Containers to Docker Compose

Where manual multi-container setups break down

Session 01 ended with two commands: create a network, then start MySQL attached to it with a volume and an environment variable. Add a second service — a PHP application that needs its own image build, its own port mapping, and the same network — and the number of flags to get right, in the right order, every single time, grows fast. Typos and forgotten flags are the normal failure mode here, not the exception.

docker-compose.yml: the whole application in one file

services:
  db:
    image: mysql:8
    environment:
      MYSQL_ROOT_PASSWORD: changeme
      MYSQL_DATABASE: labdb
      MYSQL_USER: labuser
      MYSQL_PASSWORD: labpass
    volumes:
      - mysql-data:/var/lib/mysql

  web:
    build: ./php
    ports:
      - "8082:80"
    volumes:
      - ./php:/var/www/html
    depends_on:
      - db

volumes:
  mysql-data:

This single file declares everything Session 01 did by hand: an image for each service (or a build context, for the PHP service that needs a custom Dockerfile), the volumes each one needs, the port mapping for the service that should be reachable from the host, and depends_on to hint at startup order. Compose also creates a project-scoped network automatically and attaches every service to it — no separate docker network create required.

Building a PHP image that can talk to MySQL

# php/Dockerfile
FROM php:8.2-apache
RUN docker-php-ext-install pdo pdo_mysql

The stock php:apache image runs PHP and Apache, but it has no MySQL driver installed. docker-php-ext-install pdo pdo_mysql adds the PDO extension and its MySQL driver at build time, which is what makes a new PDO(...) call in index.php actually able to reach a MySQL server.

Service discovery: names, not IPs

$pdo = new PDO(
  "mysql:host=db;dbname=labdb",
  "labuser",
  "labpass"
);

Notice the host is literally the string db — the service name from docker-compose.yml, not an IP address. This is the exact same name-based resolution from Session 01's lab-net, except Compose sets up the network and the DNS for you automatically, keyed off whatever you named each service.

depends_on controls start order, not readiness. Compose will start the db container before web, but MySQL can take a few seconds to finish initializing after its process starts. A PHP request that arrives too early can still fail to connect — production setups typically add a retry loop or a proper healthcheck, which is outside the scope of today's lab but worth knowing about.

4. Lab

Lab objective: Build a custom PHP image with the MySQL driver, connect it to MySQL manually first, then replace the manual setup with a single docker-compose.yml and verify the full stack in a browser.
1

Build a PHP + Apache image with the MySQL driver

# php/Dockerfile
FROM php:8.2-apache
RUN docker-php-ext-install pdo pdo_mysql
docker build -t php-with-mysql ./php

Before running it: predict whether this container alone, with no network flag, will be able to reach the mysql-lab container from Session 01. Confirm your prediction once you get to step 2.

2

Run the PHP container connected to MySQL manually

docker run -d --name php-lab --network lab-net -p 8082:80 \
  -v "$(pwd)/php":/var/www/html \
  php-with-mysql

This reuses the lab-net network and mysql-lab container from Session 01. Without --network lab-net, php-lab would have no way to resolve the hostname mysql-lab at all — confirm this matches what you predicted in step 1.

3

Write the final index.php

<?php
$pdo = new PDO(
  "mysql:host=mysql-lab;dbname=labdb",
  "root",
  "changeme"
);
$stmt = $pdo->query("SELECT msg FROM notes LIMIT 1");
$row = $stmt->fetch();
echo "<h1>" . htmlspecialchars($row['msg']) . "</h1>";

Save this as php/index.php, then visit http://localhost:8082. You should see the row you inserted back in Session 01's persistence experiment.

4

Tear down the manual containers

docker rm -f php-lab mysql-lab

The volume and network stay — only the containers are removed. This sets up the next step: proving Compose reproduces the same working application from a clean slate.

5

Write docker-compose.yml

services:
  db:
    image: mysql:8
    environment:
      MYSQL_ROOT_PASSWORD: changeme
      MYSQL_DATABASE: labdb
      MYSQL_USER: labuser
      MYSQL_PASSWORD: labpass
    volumes:
      - mysql-data:/var/lib/mysql

  web:
    build: ./php
    ports:
      - "8082:80"
    volumes:
      - ./php:/var/www/html
    depends_on:
      - db

volumes:
  mysql-data:

Update php/index.php's host from mysql-lab to db, matching the service name in this file, before continuing.

6

Bring the whole stack up with one command

docker compose up -d
docker compose ps

Before checking the browser: predict whether the row from Session 01 will appear immediately, given that mysql-data already contains it. Then visit http://localhost:8082 and confirm.

7

Verify the full stack end to end

Confirm the message from the database actually renders on the page — not just that docker compose ps shows both services as "Up". This is the difference between containers running and an application working.

8

Clean up

docker compose down
docker image prune -a
docker volume prune

Predict which of these commands, if any, would delete the row you've been carrying since Session 01 — then decide whether you actually want to run docker volume prune right now.

8. Post-Coding Quiz

Question 1 of 5

In docker-compose.yml, the web service has build: ./php instead of image: .... What does this mean?

build tells Compose to construct the image itself from a Dockerfile in the given directory, rather than pulling an existing image by name.
Question 2 of 5

You run docker compose down, then docker compose up -d again. What happens to the row stored in mysql-data?

docker compose down stops and removes containers and the default network, but named volumes are preserved unless you explicitly pass the -v flag.
Question 3 of 5

Why does index.php connect to host "db" instead of "mysql-lab" once the stack is defined in Compose?

Compose resolves hostnames by service name as declared in the YAML file, so the connection string has to match whatever the service is actually called there.
Question 4 of 5

depends_on ensures the db service container starts before web. What does it NOT guarantee?

depends_on only sequences container start order, not application-level readiness. MySQL can still be initializing when web's first request arrives.

9. Reflection Questions

  1. Before running docker compose up, did you correctly predict the old row would still be there? What told you the answer, given what you already knew about volumes from Session 01?
  2. Why do you think Compose separates "start order" (depends_on) from "readiness" instead of just waiting for the database to be fully ready?

10. What Breaks If This Knowledge Is Missing?

  • Skip building a custom PHP image: index.php's PDO connection fails immediately with a "driver not found" error, because the stock php:apache image has no MySQL support at all.
  • Hardcode "mysql-lab" as the host instead of the Compose service name: The connection silently fails once the app moves off Session 01's manual containers, since Compose's network only resolves the names declared in docker-compose.yml.
  • Assume depends_on means "ready", not just "started": Intermittent connection failures appear right after docker compose up, especially on a fresh volume where MySQL needs longer to initialize — a flaky bug that looks random but has a specific, well-understood cause.

11. What We Learned

Today you learned: Docker Compose replaces a sequence of manual docker run/network/volume commands with one declarative YAML file, a service's name in that file becomes its hostname on the network Compose creates automatically, a custom Dockerfile is often needed to add drivers a base image lacks, and depends_on controls start order but never guarantees application readiness.
