Layer 4 Session 09 Ingress & TLS

Ingress Routing (Raw Kubernetes, Helm, and Terraform)

Session 08 used the Terraform Helm provider to deploy a chart entirely as code — but nothing outside the cluster could reach it yet. Today the app gets a real hostname. You will route a single hostname to a running service three separate ways: a hand-written Ingress manifest, an Ingress template inside a Helm chart, and an Ingress declared through Terraform's Helm provider. Same routing objective, three tools, one mental model.

Estimated time: 55–65 minutes  ·  Flow: Pre-quiz → Concept → Lab → Commit → Post-quiz

  2. 2/6Install the ingress-nginx controller with Helm and confirm it is running
  3. 3/6Write a raw Ingress manifest that routes one hostname and multiple paths to different Services
  4. 4/6Express the same routing rules as a Helm chart template driven by values.yaml
  5. 5/6Express the same routing rules a third time using Terraform's helm_release resource
  6. 6/6Use sslip.io or a hosts-file edit to simulate DNS locally without a real domain

2. Pre-Coding Quiz

Answer before reading the concept. Need 4/5 to proceed.

Question 1 of 5

What does an Ingress resource do on its own, with no controller installed?

An Ingress resource is declarative configuration only. Without a controller watching for Ingress objects, nothing in the cluster acts on it.
Question 2 of 5

Which Kubernetes object actually runs as pods and does the traffic routing?

ingress-nginx (or any other controller) is the workload that reads Ingress resources and configures a real reverse proxy to match them.
Question 3 of 5

An Ingress rule routes diner.local/menu to menu-svc and diner.local/drinks to drinks-svc. What determines which backend a request hits?

The controller matches the incoming request's Host header and URL path against the rules and forwards to the Service listed for that match.
Question 4 of 5

Why would a lab use a hosts-file edit or sslip.io instead of a real registered domain?

A hostname-based Ingress rule needs the hostname to resolve to the cluster's IP somehow. A hosts-file edit or a wildcard service like sslip.io provides that resolution without buying or configuring a real domain.
Question 5 of 5

Today's lab expresses the same Ingress routing three different ways. What stays constant across all three approaches?

Raw YAML, a Helm template, and a Terraform helm_release all produce the same underlying Ingress object in the cluster. Only the authoring tool changes.

3. The Concept — One Route, Three Tools

Ingress resource vs. Ingress controller

These two names get used interchangeably by beginners, but they are different things. The Ingress resource is a piece of YAML describing routing rules — which hostnames and paths should map to which Services. The Ingress controller is a running workload, usually a set of pods, that watches the cluster for Ingress resources and configures an actual reverse proxy (commonly NGINX) to match them. Creating an Ingress resource with no controller installed changes nothing about how traffic flows — it just sits there, unread.

Every approach in this session assumes ingress-nginx is already installed as the controller. Only the way the rules get authored changes between approaches.

Approach 1: Raw Kubernetes Ingress

The most direct approach: install the controller with Helm, then write the Ingress rule by hand as a plain manifest and apply it with kubectl. 

helm repo add ingress-nginx https://kubernetes.github.io/ingress-nginx
helm repo update

helm install ingress-nginx ingress-nginx/ingress-nginx \
  --namespace ingress-nginx \
  --create-namespace

With the controller running, a sample backend and its Ingress rule:

# app-deployments.yaml — two tiny backends to route between
apiVersion: apps/v1
kind: Deployment
metadata:
  name: diner-menu
spec:
  replicas: 1
  selector:
    matchLabels: { app: diner-menu }
  template:
    metadata:
      labels: { app: diner-menu }
    spec:
      containers:
      - name: echo
        image: hashicorp/http-echo:1.0.0
        args: ["-text=menu ok"]
        ports: [{ containerPort: 5678 }]
---
apiVersion: v1
kind: Service
metadata:
  name: diner-menu-svc
spec:
  selector: { app: diner-menu }
  ports: [{ port: 80, targetPort: 5678 }]
# ingress.yaml — routes one host, two paths, two backends
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: diner-ingress
  annotations:
    nginx.ingress.kubernetes.io/ssl-redirect: "false"
spec:
  ingressClassName: nginx
  rules:
  - host: diner.local
    http:
      paths:
      - path: /menu
        pathType: Prefix
        backend:
          service:
            name: diner-menu-svc
            port: { number: 80 }
      - path: /drinks
        pathType: Prefix
        backend:
          service:
            name: diner-drinks-svc
            port: { number: 80 }

ingressClassName: nginx is what tells the ingress-nginx controller specifically that this rule belongs to it — a cluster can run more than one Ingress controller, and this field is how a rule picks which one should serve it. pathType: Prefix means any request path starting with /menu matches that rule.

Approach 2: Ingress via Helm

Instead of a static YAML file, the same Ingress object becomes a template inside a Helm chart, with the actual hostname and paths supplied through values.yaml. This is what helm create diner-app scaffolds, trimmed to the relevant part: 

# templates/ingress.yaml (inside the chart)
{{- if .Values.ingress.enabled -}}
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: {{ include "diner-app.fullname" . }}
  {{- with .Values.ingress.annotations }}
  annotations:
    {{- toYaml . | nindent 4 }}
  {{- end }}
spec:
  {{- with .Values.ingress.className }}
  ingressClassName: {{ . }}
  {{- end }}
  rules:
    {{- range .Values.ingress.hosts }}
    - host: {{ .host | quote }}
      http:
        paths:
          {{- range .paths }}
          - path: {{ .path }}
            pathType: {{ .pathType }}
            backend:
              service:
                name: {{ include "diner-app.fullname" $ }}
                port: { number: {{ $.Values.service.port }} }
          {{- end }}
    {{- end }}
{{- end }}
# values.yaml
ingress:
  enabled: true
  className: nginx
  annotations:
    nginx.ingress.kubernetes.io/ssl-redirect: "false"
  hosts:
    - host: diner.127.0.0.1.sslip.io
      paths:
        - path: /
          pathType: Prefix
helm install diner ./diner-app -f values.yaml
kubectl get ingress -n diner-lab

Nothing about the underlying Ingress object changed — the rendered manifest is functionally the same shape as approach 1. The difference is that the hostname, path, and annotations are now parameters, so the same chart can be reinstalled with a different hostname without touching the template.

Approach 3: Ingress via Terraform

Session 08 introduced Terraform's helm_release resource to install a Helm chart entirely from Terraform. The exact same mechanism installs the diner chart from approach 2 — Terraform simply passes the ingress values as HCL instead of a YAML file: 

# main.tf
locals {
  host = "diner.${var.test_ip}.sslip.io"
}

resource "helm_release" "ingress_nginx" {
  name             = "ingress-nginx"
  repository       = "https://kubernetes.github.io/ingress-nginx"
  chart            = "ingress-nginx"
  namespace        = "ingress-nginx"
  create_namespace = true

  set {
    name  = "controller.service.type"
    value = "NodePort"
  }
}

resource "helm_release" "diner" {
  name      = "diner"
  chart     = var.diner_chart_path
  namespace = kubernetes_namespace.diner.metadata[0].name

  values = [
    yamlencode({
      ingress = {
        enabled   = true
        className = "nginx"
        hosts = [{
          host  = local.host
          paths = [{ path = "/", pathType = "Prefix" }]
        }]
      }
    })
  ]

  depends_on = [helm_release.ingress_nginx]
}

output "test_url" {
  value = "http://${local.host}:30080/"
}
terraform init
terraform apply
kubectl get ingress -n diner-lab

Terraform is not talking to Kubernetes' Ingress API directly here — it is driving helm install on your behalf, the same operation you ran by hand in approach 2. What Terraform adds is state tracking: terraform destroy removes the controller, the chart release, and every resource it created, in dependency order.

The pattern to notice: in all three approaches, the object that ends up in the cluster is the same networking.k8s.io/v1 Ingress resource, read by the same ingress-nginx controller. Raw YAML, Helm templating, and Terraform's Helm provider are three different authoring paths to an identical runtime result.

4. Lab

Lab objective: Install ingress-nginx once, then route diner.local (or an sslip.io hostname) to a sample app three separate ways — raw manifest, Helm chart, Terraform helm_release — confirming each one serves the same routed response.
1

Install the Ingress controller

helm repo add ingress-nginx https://kubernetes.github.io/ingress-nginx
helm repo update
helm install ingress-nginx ingress-nginx/ingress-nginx \
  --namespace ingress-nginx --create-namespace

kubectl get pods -n ingress-nginx
kubectl get svc -n ingress-nginx

Predict before running: how many pods do you expect in ingress-nginx? Confirm the controller pod reaches Running before moving on.

2

Approach 1 — apply the raw manifest

Create the two backend Deployments/Services and ingress.yaml from the Concept section, then apply them:

kubectl apply -f app-deployments.yaml
kubectl apply -f ingress.yaml
kubectl get ingress

Map the hostname locally, then test in a browser or with curl:

# Windows: edit C:\Windows\System32\drivers\etc\hosts
127.0.0.1 diner.local
curl http://diner.local/menu
curl http://diner.local/drinks

Stop and think: before running the curl commands, predict which text each one returns. Then check — did /menu and /drinks each reach the backend you expected?

3

Tear down approach 1, then build approach 2 — Helm chart

kubectl delete -f ingress.yaml
kubectl delete -f app-deployments.yaml

helm create diner-app

Replace the generated templates/ingress.yaml and values.yaml ingress block with the versions from the Concept section, pointing hosts[0].host at diner.127.0.0.1.sslip.io. Install it:

helm install diner ./diner-app -f values.yaml
kubectl get ingress -n diner-lab
curl http://diner.127.0.0.1.sslip.io:30080/

Confirm the response matches what the raw-YAML version returned in step 2 — same routing outcome, different authoring path.

4

Approach 3 — drive the same chart from Terraform

Create main.tf, providers.tf, variables.tf, and versions.tf as shown in the Concept section, pointing diner_chart_path at the chart you built in step 3.

terraform init
terraform apply

Predict before running: will Terraform reinstall ingress-nginx if it's already running from step 1? Check the plan output before confirming apply, then verify:

kubectl get ingress -n diner-lab
curl http://diner.127.0.0.1.sslip.io:30080/
5

Clean up

terraform destroy
helm uninstall diner -n diner-lab
helm uninstall ingress-nginx -n ingress-nginx

Confirm with kubectl get ingress -A that no Ingress resources remain.

7. Code Review Checklist

8. Post-Coding Quiz

Question 1 of 5

In the raw Ingress manifest, what does ingressClassName: nginx actually accomplish?

A cluster can run multiple Ingress controllers side by side. ingressClassName is how a rule declares which one should read and act on it.
Question 2 of 5

What actually changes between the raw-YAML, Helm, and Terraform approaches used in this lab?

All three approaches end with the same networking.k8s.io/v1 Ingress object read by the same controller. Only the authoring and apply mechanism differs.
Question 3 of 5

Why does sslip.io let a hostname like diner.127.0.0.1.sslip.io resolve without any DNS configuration?

sslip.io parses the IP address out of the hostname's own text and returns it as the DNS answer — no records need to be created ahead of time.
Question 4 of 5

In the Terraform approach, what does helm_release actually do under the hood?

helm_release is Terraform's wrapper around the Helm client — it performs the same install/upgrade Helm would, while recording the release in Terraform's state file.

9. Reflection Questions

  1. Which of the three approaches — raw YAML, Helm, or Terraform — felt fastest to write, and which felt safest to change later? Why might those be different answers?
  2. If a teammate only had the Terraform files from approach 3, could they reconstruct what the actual Ingress rule looks like without running terraform plan? What does that suggest about readability trade-offs?
  3. What would break if ingressClassName were left out of the raw manifest entirely, in a cluster running two different Ingress controllers?

10. What Breaks If This Knowledge Is Missing?

  • Confusing the Ingress resource with the controller: a team applies routing rules, sees nothing happen, and wastes time debugging YAML that was never the problem — the controller was never installed.
  • Skipping ingressClassName in a multi-controller cluster: the rule may be picked up by the wrong controller, or by none, producing routing that appears to work in a single-controller test cluster but fails in a shared production cluster.
  • Not recognizing that all three approaches produce the same object: a team might treat a Terraform-managed Ingress and a Helm-managed one as fundamentally different systems, duplicating routing logic instead of reusing the same chart.

11. What We Learned

Today you learned: an Ingress resource is inert without a running Ingress controller, the same routing objective can be expressed as raw YAML, a Helm chart template, or a Terraform helm_release, and all three converge on the identical object read by the identical controller — only the authoring tool changes.
