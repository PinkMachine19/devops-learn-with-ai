Layer 6 Session 14 Observability & Landscape

Observability with Prometheus and Grafana

Session 13 proved a canary rollout works by hammering it with request loops and eyeballing which color came back. That approach does not scale past a lab — a real rollout needs a way to watch error rate and latency change in near real time, without writing a PowerShell loop every time. This session installs Prometheus to scrape metrics from the cluster and Grafana to visualize them, so the next canary or blue-green release you run can be watched on a dashboard instead of guessed at.

Estimated time: 45–55 minutes · Flow: Pre-quiz → Concept → Lab → Commit → Post-quiz

1. Learning Objectives

  1. 1/5Distinguish observability from plain monitoring: understanding why, not just knowing that
  2. 2/5Install Prometheus and Grafana via Helm into an isolated monitoring namespace
  3. 3/5Explain the pull-based scrape model and how it differs from a push-based agent
  4. 4/5Write basic PromQL queries using rate(), labels, and filtering
  5. 5/5Build a Grafana dashboard connected to Prometheus and compare it against kubectl top

2. Pre-Coding Quiz

Answer before reading the concept. Need 4/5 to proceed.

Question 1 of 5

What is the core difference between monitoring and observability?

Monitoring answers "did a threshold get crossed." Observability is about having rich enough data — metrics, labels, history — to investigate questions nobody thought to alert on ahead of time.
Question 2 of 5

How does Prometheus collect metrics from a target by default?

Prometheus is pull-based — it periodically requests /metrics from each configured target rather than waiting for applications to send data to it.
Question 3 of 5

What role does Grafana actually play in this stack?

Grafana is a visualization layer. It sends PromQL queries to a configured Prometheus data source on demand and draws whatever comes back.
Question 4 of 5

Why can kubectl top and a Prometheus dashboard show slightly different numbers for the same pod?

kubectl top is powered by the lightweight Metrics Server, which keeps only a recent snapshot. Prometheus scrapes and retains history with full label detail, so exact values can differ slightly.
Question 5 of 5

What does wrapping a counter metric in rate(...) actually compute?

rate() converts an ever-increasing counter into a usable per-second trend over the specified window, which is what actually makes sense plotted on a graph.

3. The Concept — Metrics, Scraping, and Dashboards

Observability is a bigger idea than monitoring

Monitoring is asking "is X currently broken." It works well for questions you thought to ask in advance — an alert on error rate, a threshold on CPU. Observability is the broader property of a system being genuinely understandable from its outputs: metrics, logs, and traces detailed enough that you can investigate a question you never pre-wrote an alert for. Prometheus and Grafana are the metrics half of that picture — they do not replace logs or traces, but they are usually the first piece a team builds.

Prometheus: a pull-based metrics database

Prometheus does not wait for applications to send it data. It is configured with a list of scrape targets and, on an interval, sends an HTTP request to each target's /metrics endpoint, parsing whatever plaintext metrics come back. This pull model means a target simply has to expose a well-known endpoint — it never needs to know Prometheus exists, let alone where it lives. 

helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm repo add grafana https://grafana.github.io/helm-charts
helm repo update

kubectl create namespace monitoring
helm install prometheus prometheus-community/prometheus -n monitoring

Installing the Prometheus Helm chart deploys several components — a server, an alertmanager, and exporters — but the important mental model for this session is just: it scrapes, it stores, it answers PromQL queries.

Grafana: queries Prometheus, owns no data

helm install grafana grafana/grafana -n monitoring \
  --set service.type=NodePort \
  --set persistence.enabled=false \
  --set adminPassword='admin'

kubectl port-forward svc/grafana 3000:80 -n monitoring
Lab-only setting: a hardcoded admin password and disabled persistence are fine for a local learning cluster. Neither belongs in a real deployment — use a secret manager for the password and enable persistence so dashboards survive a pod restart.

Inside the Grafana UI, add a data source of type Prometheus pointing at Prometheus's in-cluster service DNS name: 

http://prometheus-server.monitoring.svc.cluster.local

That URL works because Kubernetes gives every Service a stable DNS name of the form <service>.<namespace>.svc.cluster.local — Grafana never needs a hardcoded IP address, and the same URL keeps working across restarts and rescheduling.

PromQL fundamentals

container_memory_usage_bytes
rate(container_cpu_usage_seconds_total[5m])
kube_pod_container_status_restarts_total

A bare metric name like container_memory_usage_bytes returns the current value for every label combination Prometheus has seen — one line per pod, per container, per node. Filtering by label narrows that down, and wrapping a counter in rate() turns an ever-climbing total into a usable per-second trend: 

rate(container_cpu_usage_seconds_total{namespace="diner-lab"}[5m])
sum(rate(container_cpu_usage_seconds_total{namespace="diner-lab"}[5m])) by (pod)

sum(...) by (pod) aggregates the per-container rate up to one line per pod — the aggregation functions (sum, avg, max) and the by grouping clause are what turn a wall of raw label combinations into a readable graph.

Importing real dashboards instead of building from zero

Grafana's dashboard import feature accepts a numeric dashboard ID from the public Grafana dashboard library. Dashboard 315 (Kubernetes Pods Resources) and 6417 (NGINX Ingress) are widely used community dashboards that render correctly against a standard kube-prometheus-style install without any manual panel building.

Metrics Server vs Prometheus

kubectl top pods is powered by the Metrics Server, a lightweight component that keeps only a brief in-memory snapshot of CPU and memory — enough for kubectl top and the HPA from Session 12, nothing more. Prometheus is a different system entirely: it retains history, tracks arbitrary labels, and answers arbitrary PromQL — which is why the two can report legitimately different numbers for the same pod at the same moment without either being "wrong."

4. Lab

Lab objective: Install Prometheus and Grafana via Helm into a dedicated monitoring namespace, connect Grafana to Prometheus, import a dashboard, and generate synthetic load to watch metrics move.
1

Add Helm repos and create the namespace

helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm repo add grafana https://grafana.github.io/helm-charts
helm repo update
kubectl create namespace monitoring
2

Install Prometheus and verify it is scraping

helm install prometheus prometheus-community/prometheus -n monitoring
kubectl get pods -n monitoring
kubectl get svc -n monitoring

Predict before running: which Service name do you expect to use as the Prometheus data source URL inside Grafana in step 4? Write it down, then confirm against the actual Service list.

3

Install Grafana and port-forward to it

helm install grafana grafana/grafana -n monitoring `
  --set service.type=NodePort `
  --set persistence.enabled=false `
  --set adminPassword='admin'
kubectl port-forward svc/grafana 3000:80 -n monitoring

Open http://localhost:3000 and log in with username admin and the password set above.

4

Add Prometheus as a data source

In Grafana: Connections → Data sources → Add data source → Prometheus. Set the URL to http://prometheus-server.monitoring.svc.cluster.local, then Save & test. A green confirmation means Grafana successfully queried Prometheus.

5

Import dashboards 315 and 6417

Dashboards → New → Import. Enter dashboard ID 315 (Kubernetes Pods Resources), select the Prometheus data source, and load it. Repeat with ID 6417 (NGINX Ingress). Confirm panels render data for the diner-lab namespace.

6

Run PromQL queries directly

container_memory_usage_bytes
rate(container_cpu_usage_seconds_total[5m])
kube_pod_container_status_restarts_total

Try each in Prometheus's own Graph UI or Grafana's Explore view. Note which labels are attached to each result — namespace, pod, container — and filter one query down to just namespace="diner-lab".

7

Compare kubectl top against the dashboard

kubectl top pods -n diner-lab

Stop and think: before comparing, predict whether the numbers will match exactly. Then check the Kubernetes Pods Resources dashboard for the same pods and note any difference — and explain why, using the Metrics Server vs Prometheus distinction from the Concept section.

8

Optional: generate synthetic load and watch it spike

kubectl run loadgen --image=busybox --restart=Never -n diner-lab -- sh -c "while true; do wget -q -O- http://diner-stable-svc >/dev/null; done"

Watch the imported dashboards for a visible spike, then clean up the load generator: kubectl delete pod loadgen -n diner-lab.

9

Cleanup

helm uninstall grafana -n monitoring
helm uninstall prometheus -n monitoring
kubectl delete ns monitoring

Question 1 of 5

Why does Grafana's Prometheus data source use a cluster DNS name instead of a pod IP address?

A Kubernetes Service gets a predictable DNS name of the form service.namespace.svc.cluster.local that keeps resolving correctly no matter how many times the underlying pods are rescheduled.
Question 2 of 5

What does rate(container_cpu_usage_seconds_total[5m]) actually return?

rate() is specifically built to turn an ever-increasing counter into a usable per-second average over the given window, matching the PromQL fundamentals covered in the Concept section.
Question 3 of 5

kubectl top pods and a Grafana dashboard show slightly different memory values for the same pod at the same time. What is the most likely explanation?

This is the exact distinction the lab asked you to verify hands-on: Metrics Server and Prometheus are separate systems with separate collection cadences, so small differences are expected and not a bug.
Question 4 of 5

A teammate asks why the loadgen pod's requests do not show up in the dashboard right away. What is the most likely reason?

Because Prometheus is pull-based and scrapes on a fixed interval rather than instantly, there is always a small lag between something happening and it appearing in a query result.

10. What Breaks If This Knowledge Is Missing?

  • Treating monitoring and observability as the same thing: A team that only sets up threshold alerts will be blind to problems nobody thought to alert on — the entire point of observability is answering questions asked after the fact.
  • Assuming Prometheus pushes data: Debugging "why isn't this metric showing up" goes nowhere if you assume the app pushes data — the actual fix is almost always about the scrape target configuration, since Prometheus always pulls.
  • Skipping the Metrics Server vs Prometheus distinction: A team that sees kubectl top and a dashboard disagree and assumes one is broken will waste time debugging a non-issue instead of understanding they are simply different data sources.
  • Hardcoding a Grafana data source IP instead of the Service DNS name: The dashboard silently breaks the next time Prometheus's pod reschedules, because a pod IP is not stable across restarts.

11. What We Learned

Today you learned: observability is broader than monitoring, Prometheus is a pull-based metrics database that scrapes /metrics endpoints on an interval, Grafana queries Prometheus with PromQL to render dashboards without storing data itself, and kubectl top and Prometheus report from genuinely different sources — the Metrics Server's live snapshot versus Prometheus's scraped history.
