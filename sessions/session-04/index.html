Layer 2 Session 04 Kubernetes

Namespaces and Resource Quotas

Session 03 deployed, exposed, scaled, and rolled out an app entirely inside the default namespace, as if the cluster only had one tenant. Real clusters don't work that way — multiple teams and workloads share the same nodes, and nothing stops one noisy Deployment from starving everyone else's pods of CPU. Today: carving out an isolated namespace of your own, and putting a hard ceiling on what it's allowed to consume.

Estimated time: 35–45 minutes

Pre-quiz → Concept → Lab → Commit → Post-quiz

2. Pre-Coding Quiz

Answer before reading the concept. Need 4/5 to proceed.

Question 1 of 5

What is a Kubernetes namespace, most precisely?

A namespace groups and scopes objects within a single cluster; it does not add hardware or create a new cluster.
Question 2 of 5

Which namespace exists on a brand-new cluster before you create anything yourself?

kube-system, along with default, kube-public, and kube-node-lease, is created automatically when the cluster comes up.
Question 3 of 5

What does adding -n sandbox to a single kubectl get pods command do?

The -n flag is per-command. Changing the lasting default requires kubectl config set-context --current --namespace=sandbox instead.
Question 4 of 5

What can a ResourceQuota object limit inside a namespace?

A ResourceQuota sets hard caps on aggregate consumption within a namespace, commonly pod count plus CPU/memory requests and limits, and optionally counts of other object types.
Question 5 of 5

A namespace's ResourceQuota already has 3 of 3 allowed pods running. What happens if you try to create a 4th?

The API server checks the quota at request time and refuses the create call with an "exceeded quota" error — nothing gets created and nothing else is touched.

3. The Concept — Isolating and Capping Workloads

What a namespace is, and is not

A namespace is a way of dividing one cluster into multiple virtual sub-clusters. Object names only need to be unique within a namespace, so two teams can each have a Deployment named web without colliding, as long as they live in different namespaces. That's the whole mechanism: a grouping and naming boundary, enforced by the API server when you list, create, or reference objects.

It is important to be precise about what a namespace does not give you by itself. Namespaces are a soft isolation boundary, not a security boundary. Without additional controls — network policies, RBAC rules, pod security standards — a pod in one namespace can still be reached over the network by a pod in another, and a cluster-admin identity can still act across every namespace. Namespaces organize; they don't wall off traffic or privileges on their own.

The namespaces that already exist

kubectl get ns

Every cluster ships with four namespaces before you create anything:

  • default — where objects land if you never specify a namespace
  • kube-system — control-plane components like the scheduler and DNS
  • kube-public — readable by all users cluster-wide, rarely used in practice
  • kube-node-lease — tracks node heartbeats for failure detection

Creating and listing namespaces

kubectl create namespace sandbox
kubectl get ns

Creating a namespace produces an empty object — no pods, no Services, nothing inside it — until you deploy something there explicitly.

Scoping commands: -n versus the context default

# Scope a single command with -n
kubectl create deployment web --image=nginx -n sandbox
kubectl get pods -n sandbox

# Or change what "no -n" means for every future command
kubectl config set-context --current --namespace=sandbox
kubectl get pods   # now targets sandbox automatically

-n is a one-off override for a single command. kubectl config set-context --current --namespace=sandbox changes the current context's default namespace, so every later command that omits -n targets sandbox until you switch it back. Both approaches scope the same way; they differ only in how long the scoping lasts.

What a ResourceQuota can limit

A ResourceQuota is a namespaced object that sets hard caps on totals within that namespace: the number of pods, the sum of CPU and memory requests, the sum of CPU and memory limits, and optionally counts of other object types such as Services or ConfigMaps. A current best-practice manifest looks like this: 

apiVersion: v1
kind: ResourceQuota
metadata:
  name: sandbox-quota
  namespace: sandbox
spec:
  hard:
    pods: "3"
    requests.cpu: "1"
    requests.memory: 1Gi
    limits.cpu: "2"
    limits.memory: 2Gi
kubectl apply -f sandbox-quota.yaml
kubectl describe quota -n sandbox

describe quota prints a table of each tracked resource with its current usage next to its hard limit, so you can see at a glance how close a namespace is to its ceiling.

What happens when a quota is exceeded

Once a ResourceQuota exists in a namespace, the API server checks every relevant create request against it before admitting the object. If creating a fourth pod would push the namespace's pod count past a pods: "3" limit, the request is rejected immediately with a "forbidden: exceeded quota" error — the pod is never created, and nothing already running is affected.

4. Lab

Lab objective: Create a sandbox namespace, deploy nginx inside it, switch your kubectl context's default namespace to it, then apply a ResourceQuota and confirm it's actually enforced.
1

List existing namespaces

kubectl get ns

You should see default, kube-system, kube-public, and kube-node-lease already present.

2

Create a sandbox namespace

kubectl create namespace sandbox
kubectl get ns

sandbox should now appear in the list, empty.

3

Deploy nginx inside sandbox only

kubectl create deployment web --image=nginx -n sandbox
4

Verify the pods exist only in sandbox

kubectl get pods -n sandbox
kubectl get pods            # default namespace — should NOT show "web"
5

Switch the context's default namespace to sandbox

kubectl config set-context --current --namespace=sandbox
kubectl get pods            # now targets sandbox without -n
6

Write and apply a ResourceQuota

# sandbox-quota.yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: sandbox-quota
  namespace: sandbox
spec:
  hard:
    pods: "3"
    requests.cpu: "1"
    requests.memory: 1Gi
    limits.cpu: "2"
    limits.memory: 2Gi
kubectl apply -f sandbox-quota.yaml

Predict first: the quota above caps sandbox at 3 pods total. The web Deployment currently has 1 replica running. Before you do anything else, write down what you expect to happen if you scale web up to 4 replicas.

7

Observe: scale past the quota

kubectl scale deployment web --replicas=4 -n sandbox
kubectl describe quota sandbox-quota -n sandbox
kubectl get pods -n sandbox

Compare the actual result to your prediction. You should see the pod count in describe quota stop at the hard limit, and only 3 pods listed, with events showing the 4th create request forbidden for exceeding quota.

8

Clean up

kubectl delete ns sandbox
kubectl config set-context --current --namespace=default
kubectl get ns

Deleting the namespace removes everything inside it — the Deployment, its pods, and the ResourceQuota — in one step. Restoring the context's default namespace avoids surprises in the next session.

8. Post-Coding Quiz

Question 1 of 5

You scale a Deployment in sandbox to 4 replicas, but its ResourceQuota caps pods at 3. What is left running?

The quota is enforced per create request. Three pods that were already admitted keep running; the fourth is refused before it's ever created.
Question 2 of 5

Why is a namespace described as a "soft" isolation boundary rather than a security boundary?

Namespaces organize and name-scope objects, but reaching a pod over the network or acting across namespaces still requires separate controls like network policies and RBAC.
Question 3 of 5

kubectl config set-context --current --namespace=sandbox was run. What does a plain kubectl get pods (no -n) target now?

Changing the current context's namespace changes what "no -n" means for every subsequent command until it's changed again.
Question 4 of 5

kubectl delete ns sandbox is run while a Deployment, its pods, and a ResourceQuota still exist inside it. What happens to those objects?

Deleting a namespace deletes everything scoped to it in one step — there is no automatic migration of objects to another namespace.

9. Reflection Questions

  1. Before scaling past the quota's pod limit, did you correctly predict the create request would be rejected rather than degraded or queued? What was your reasoning beforehand?
  2. Why is a namespace, by itself, not enough to stop one workload from consuming the whole cluster's CPU?
  3. What would you need to add on top of namespaces and a ResourceQuota to also stop pods in different namespaces from talking to each other over the network?

10. What Breaks If This Knowledge Is Missing?

  • Everything left in the default namespace: unrelated teams' Deployments, Services, and ConfigMaps all share one flat namespace, so a name collision (two teams both deploying "web") becomes a real outage, not a hypothetical.
  • No ResourceQuota anywhere: one noisy-neighbor workload — a runaway batch job or a bug causing endless pod restarts — can consume all available cluster CPU and memory, starving every other namespace with no warning and no enforced ceiling.
  • Never switching the kubectl context: every command needs -n typed manually, and the one time it's forgotten, an object silently lands in the wrong namespace.
  • Deleting a namespace without checking what's inside it: a Deployment, quota, or Secret that someone still needed disappears with no separate confirmation per object.

11. What We Learned

Today you learned: a namespace divides one cluster into logical, independently-named groups without being a security boundary on its own; -n scopes a single command while set-context changes the lasting default; and a ResourceQuota puts a hard, API-server-enforced ceiling on pod count, CPU, and memory per namespace.
