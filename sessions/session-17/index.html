Layer 7 Session 17 Capstone: Ship a Real App

Capstone: CI Pipeline with GitHub Actions

Session 16 built the Text Masker app — a small Node/Express API paired with a static client — and packaged both halves into Docker images by hand, running docker build yourself every time something changed. Today that manual step disappears. A GitHub Actions workflow is wired up so that every push to main automatically builds both images fresh and pushes them to a container registry, with no local docker build required ever again.

Estimated time: 35–45 minutes

Flow: Pre-quiz → Concept → Lab → Commit → Post-quiz

2. Pre-Coding Quiz

Answer before reading the concept. Need 4/5 to proceed.

Question 1 of 5

What is a workflow "trigger" in GitHub Actions?

The `on:` block defines the trigger — the event GitHub watches for, such as a push to a specific branch, that starts the workflow run.
Question 2 of 5

Inside a job, what is a "step"?

A job runs its steps sequentially, top to bottom, on one runner — checkout, then setup, then login, then build and push are each a step.
Question 3 of 5

Why use GitHub Secrets instead of writing the Docker Hub password directly in the workflow file?

A workflow file is committed to the repo history for anyone with read access to see. Secrets stay encrypted on GitHub and are only injected at run time.
Question 4 of 5

What does docker/build-push-action do?

build-push-action combines the build and push into a single step, using the context and Dockerfile you point it at, then uploading the result.
Question 5 of 5

Once the workflow is committed, what happens on every future push to main?

That's the entire point of CI here: any push landing on main re-triggers the workflow, which rebuilds and re-pushes both images without anyone touching Docker locally.

3. The Concept — Automating the Build You Did By Hand

What CI means for this app

Session 16 ended with two Docker images built manually, on demand, whenever there was time to remember to run docker build again. Continuous integration replaces that habit with a machine that never forgets: a GitHub Actions workflow watches the repository, and the moment a commit lands on main, it checks out that exact code, builds both the server and client images from it, and pushes the results to a registry — every time, the same way, without anyone having to remember to do it.

Anatomy of a workflow file

Every workflow file under .github/workflows/ follows the same three-part shape: a trigger (when to run), one or more jobs (what runs, and on what kind of machine), and each job's ordered steps (the individual actions or commands that make up the job). 

on:
  push:
    branches: [main]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code
        uses: actions/checkout@v4
      # ...more steps below

runs-on: ubuntu-latest tells GitHub to spin up a fresh Ubuntu virtual machine for this job — nothing is left over from any previous run, which is exactly what makes the build reproducible.

Storing credentials with gh secret set

Pushing an image to Docker Hub requires a username and an access token. Neither belongs in the repository. The GitHub CLI (gh) can create encrypted repository secrets directly from the terminal, once authenticated: 

# Confirm gh is authenticated first
gh auth status

# Store the two secrets the workflow will reference
gh secret set DOCKERHUB_USERNAME
gh secret set DOCKERHUB_TOKEN

# Confirm they were created
gh secret list

Running gh secret set NAME without --body prompts for the value interactively, which keeps it out of shell history. Once set, gh secret list should show both names — never the values themselves, since GitHub does not display secret contents back to anyone once they're stored.

The actual workflow: .github/workflows/ci-cd.yml

With the repository created (for example under your-org/masker-lab) and both secrets in place, the workflow itself ties everything together: check out the code, set up Buildx, log in to Docker Hub using the two secrets, then build and push the server image followed by the client image. 

name: Build and Push Masker Images

on:
  push:
    branches: [ main ]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Set up Docker Buildx
        uses: docker/setup-buildx-action@v3

      - name: Log in to Docker Hub
        uses: docker/login-action@v3
        with:
          username: ${{ secrets.DOCKERHUB_USERNAME }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}

      - name: Build & push masker-server
        uses: docker/build-push-action@v6
        with:
          context: ./server
          push: true
          tags: ${{ secrets.DOCKERHUB_USERNAME }}/masker-server:latest

      - name: Build & push masker-client
        uses: docker/build-push-action@v6
        with:
          context: ./client
          push: true
          tags: ${{ secrets.DOCKERHUB_USERNAME }}/masker-client:latest

Each docker/build-push-action step is independent: one points its context at ./server, the other at ./client, so the two images build from their own Dockerfiles without interfering with each other.

Why secrets keep credentials out of the repo

Notice that the token never appears anywhere in ci-cd.yml itself — only the reference ${{ secrets.DOCKERHUB_TOKEN }} does. GitHub substitutes the real value at run time and also masks it out of any log output automatically, so even a public repository's Actions logs never leak the actual credential.

Monitoring runs in the Actions tab

After pushing, the Actions tab on the GitHub repository page lists every workflow run, newest first. Clicking a run shows each job, and clicking a job expands every step with its own live log — the fastest way to see exactly which step failed if something goes wrong.

Optional enhancement: tagging by commit SHA

Tagging every push as :latest works, but it overwrites history — there's no way to tell which commit produced the image currently running. Swapping the tag for ${{ github.sha }} ties each image version back to the exact commit that built it: 

tags: ${{ secrets.DOCKERHUB_USERNAME }}/masker-server:${{ github.sha }}

This is not required for today's lab, but it's the natural next step once the basic pipeline is working.

4. Lab

Lab objective: Store Docker Hub credentials as GitHub Secrets, write a working ci-cd.yml, push it, and confirm both the server and client images land in the registry.
1

Verify gh CLI authentication

gh auth status

If it reports not logged in, run gh auth login and follow the prompts: GitHub.com → HTTPS → "Login with a web browser".

2

Add the two GitHub secrets via CLI

gh secret set DOCKERHUB_USERNAME
gh secret set DOCKERHUB_TOKEN
gh secret list

Expect to see both names confirmed as created, with no values printed.

3

Create the workflow folder

mkdir -p .github/workflows
4

Write .github/workflows/ci-cd.yml

Use the full workflow shown in the concept section above — checkout, Buildx setup, Docker Hub login, then two separate build-push-action steps, one for ./server and one for ./client.

5

Predict, then push

Before running git push, write down a prediction: in the Actions tab, how many jobs will this run show, and how many build-push steps will appear inside that job?

git add .github/workflows/ci-cd.yml
git commit -m "session-17: add CI workflow to build and push Docker images"
git push
6

Watch it run in the Actions tab

Open the repository on GitHub and click Actions. Find the newest run of "Build and Push Masker Images," open it, and expand each step's log as it completes. Compare the result to your prediction from step 5.

7

Verify by pulling the images locally

docker pull $env:DOCKERHUB_USERNAME/masker-server:latest
docker pull $env:DOCKERHUB_USERNAME/masker-client:latest

docker run -d --name masker-server -p 8080:8080 $env:DOCKERHUB_USERNAME/masker-server:latest
docker run -d --name masker-client -p 30080:80 $env:DOCKERHUB_USERNAME/masker-client:latest

Visit http://localhost:8080/health and http://localhost:30080 to confirm both containers came from the pipeline, not from a local build. When done, clean up with docker rm -f masker-server masker-client.

8. Post-Coding Quiz

Question 1 of 5

The repository is public and the images are pushed to a public Docker Hub repository. What does that mean in practice?

A public Docker Hub repository is pullable by anyone with docker pull, regardless of who can see the source code — private repositories exist for exactly this reason.
Question 2 of 5

What is GitHub Container Registry (GHCR), in relation to Docker Hub?

GHCR is a registry hosted by GitHub itself. Switching to it is mostly a matter of changing the login target and the tags: line — the rest of the workflow stays the same shape.
Question 3 of 5

The workflow references secrets.DOCKERHUB_TOKEN, but the secret was actually created as DOCKERHUB_TOKEM (typo). What happens?

A misspelled secret name simply doesn't match anything, so the reference resolves to an empty string, and docker/login-action fails to authenticate with an empty password.
Question 4 of 5

Why does the workflow include a "Set up Docker Buildx" step before building?

docker/build-push-action builds through Buildx, so setup-buildx-action prepares that builder on the runner before any build-push step can run.
Question 5 of 5

Session 18 picks up right where the registry left off: continuous deployment, pulling the freshly built images down and running them without a manual docker pull.

9. Reflection Questions

  1. Before pushing, did you correctly predict how many build-push steps would show up in the Actions run? What made that easy or hard to guess?
  2. Why does it matter that the DOCKERHUB_TOKEN never appears as plain text anywhere in ci-cd.yml, even though the workflow clearly needs it to authenticate?
  3. If this repository and its Docker Hub images were switched to private, what would break for someone trying to pull the images without credentials?

10. What Breaks If This Knowledge Is Missing?

  • Hardcoding the token in ci-cd.yml instead of using secrets: the credential becomes visible to anyone who can read the repository or its commit history, defeating the entire purpose of keeping it out of source control.
  • Getting the trigger wrong (or leaving it off branch filtering): the workflow either never runs when it should, or runs on every branch push, burning Actions minutes and pushing half-finished work to the registry.
  • Not knowing where to look when a run fails: without understanding that the Actions tab breaks a run down into jobs and steps with their own logs, a failed login or build step looks like an unexplainable dead end instead of a two-minute diagnosis.

11. What We Learned

Today you learned: a GitHub Actions workflow is triggered by an event like a push to main, runs as an ordered list of jobs and steps on a fresh runner, authenticates using encrypted GitHub Secrets rather than hardcoded credentials, and uses docker/build-push-action to build and push each image straight to a registry — turning a manual docker build habit into a reproducible pipeline.
