Capstone: CD to Local Docker

Session 17 wired up continuous integration: a push to main now automatically builds both Text Masker images and pushes them to a registry. Nothing runs them, though — a human still has to notice the new images exist and manually restart containers. Today that gap closes. This session extends the same CI pipeline into real continuous deployment, so a completed build automatically redeploys the running containers on a local machine, with zero manual docker commands.

Estimated time: 40–50 minutes

2. Pre-Coding Quiz

Answer before reading the concept. Need 4/5 to proceed.

Question 1 of 5

What is the core difference between CI and CD?

CI covers build, test, and push. CD is the separate concern of taking a built artifact and actually deploying it to a running environment.
Question 2 of 5

Why does the deploy job in this lab need a self-hosted runner instead of a normal GitHub-hosted one?

A GitHub-hosted runner is an ephemeral cloud VM with no route to a developer's local Docker engine. The self-hosted runner is an agent installed on that exact workstation.
Question 3 of 5

Why use workflow_run instead of triggering the deploy workflow on push as well?

A second push trigger would fire deploy at the same time as build, possibly before new images exist. workflow_run only starts once the named workflow reaches a completed state.
Question 4 of 5

Why does deploy_local.ps1 pipe the Docker Hub token into docker login --password-stdin rather than passing it as a typed argument?

Piping the token in lets the workflow step run non-interactively and avoids the secret ever appearing as a plain command-line argument.
Question 5 of 5

What does $ErrorActionPreference = 'Stop' do at the top of deploy_local.ps1?

Without it, many PowerShell cmdlet errors just print a message and keep going, which could let a failed docker pull sail through to docker run on a stale image.

3. The Concept — Turning a Build Into a Deployment

CI vs CD, recapped

Session 17 built a workflow that runs on every push to main: it builds both Text Masker images and pushes them to a registry under tags like server-latest and client-latest. That workflow is continuous integration — new code gets validated and packaged automatically. But the containers actually running on any given machine don't change just because a new image exists in a registry somewhere. Getting that new image running is a separate job: continuous deployment. Today's session builds the CD half.

Setting up a self-hosted runner

GitHub-hosted runners are short-lived cloud virtual machines — they have no way to reach a Docker engine running on a developer's own workstation. A self-hosted runner solves this: it's a small agent process installed directly on the target machine and registered to the repository under Settings → Actions → Runners. Once registered and running, it shows up green and idle, waiting for jobs that specify runs-on: self-hosted.

One detail matters more than it looks: the runner service has to run under a user account that actually has permission to talk to Docker. If it's installed under an account without Docker group membership (or without Docker Desktop's WSL integration enabled for that user), every docker command in the deploy job fails with an access error, even though the exact same command works fine when typed manually in a terminal logged in as that user.

The deployment script

deploy_local.ps1 lives at the repo root and does five things in order: log in, stop the old containers, pull the new images, start new containers, log out. 

param([string]$DockerUser, [string]$DockerToken)
$ErrorActionPreference = 'Stop'

Write-Host 'Logging into Docker Hub...'
$DockerToken | docker login -u $DockerUser --password-stdin

Write-Host 'Stopping old containers (if running)...'
docker rm -f masker-server masker-client 2>$null

Write-Host 'Pulling latest images...'
docker pull "$DockerUser/masker:server-latest"
docker pull "$DockerUser/masker:client-latest"

Write-Host 'Starting new containers...'
docker run -d --name masker-server -p 8080:8080 "$DockerUser/masker:server-latest"
docker run -d --name masker-client -p 30080:80 "$DockerUser/masker:client-latest"

Write-Host 'Logging out of Docker Hub...'
docker logout

Write-Host 'Deployment complete!'

Image paths use a placeholder here — <your-dockerhub-username>/masker:server-latest — but in the actual script it's whatever value gets passed in for $DockerUser. Keeping server and client under one repository name with different tags (rather than two separate repositories) keeps the pull commands symmetric and easy to script.

The workflow that triggers it

name: Deploy Locally (Docker Runner)

on:
  workflow_run:
    workflows: ["Build and Push Masker Images"]
    types: [completed]

jobs:
  deploy:
    runs-on: self-hosted
    steps:
      - uses: actions/checkout@v4
      - name: Run local deployment script
        run: pwsh "${{ github.workspace }}/deploy_local.ps1" -DockerUser $env:DOCKERHUB_USERNAME -DockerToken $env:DOCKERHUB_TOKEN
        env:
          DOCKERHUB_USERNAME: ${{ secrets.DOCKERHUB_USERNAME }}
          DOCKERHUB_TOKEN: ${{ secrets.DOCKERHUB_TOKEN }}

The workflows: [...] list under workflow_run names the exact workflow this one waits on — here, whatever the CI workflow from session 17 is named (for example, "Build and Push Masker Images"). types: [completed] means this job fires whenever that workflow finishes, whether it succeeded or failed — the deploy job itself is responsible for checking github.event.workflow_run.conclusion if it needs to skip deploying on a failed build.

Why secrets get re-declared as env vars

On GitHub-hosted runners, ${{ secrets.* }} can often be referenced fairly directly in a step. On a self-hosted runner it's safer and more reliable to explicitly map each secret into an environment variable under that step's env: block, then read it inside the script as $env:DOCKERHUB_USERNAME. This keeps the secret scoped to exactly the step that needs it instead of leaking into the runner's broader shell environment, and it avoids relying on repository variables, which don't get injected into self-hosted runner jobs the same way secrets do.

Verifying the deployment

Once both workflows finish, three quick checks confirm it actually worked: 

docker ps
curl http://localhost:8080/health
start http://localhost:30080

docker ps should list both masker-server and masker-client as freshly started. The curl call hits the server's health endpoint directly. Opening localhost:30080 in a browser confirms the client is actually reachable end-to-end. Instead of hardcoding localhost or a raw IP when checking from another device on the same network, a stable local hostname (for example, one provided by a tool like Tailscale's MagicDNS) avoids the deployment breaking every time the machine gets a new IP address.

The full pipeline, end to end

One push to main now sets off a complete chain: CI builds and pushes both images, workflow_run hands off to the self-hosted runner, the runner executes deploy_local.ps1, and the local Docker engine ends up running the updated masker-server on port 8080 and masker-client on port 30080 — visible immediately in a browser. 4. Lab

Lab objective: Create the deployment script and its triggering workflow, push a change to fire the full CI→CD chain, and verify the running containers locally.

Open Settings → Actions → Runners in the repository. Confirm a runner shows an "Idle" green status. If it isn't listed at all, install and register it first, making sure the runner service is started under an account that has Docker permissions on this machine.

2

Create deploy_local.ps1 at the repo root

Add the script from the concept section above. It accepts -DockerUser and -DockerToken parameters, sets $ErrorActionPreference = 'Stop', and runs login → stop old → pull new → start new → logout in that order.

3

Create .github/workflows/deploy_local.yml

Use the workflow_run trigger keyed to the exact name of the CI workflow from session 17, run on self-hosted, and re-declare DOCKERHUB_USERNAME and DOCKERHUB_TOKEN as step-level env vars sourced from repository secrets.

4

Predict, then trigger the full chain

Before pushing: predict what docker ps will show once both workflows finish — which two container names, which two ports, and roughly how "new" their start times will be. Write it down, then commit and push a small change.

git add .
git commit -m "Trigger CD pipeline"
git push
5

Watch both workflows run in the Actions tab

Confirm the build workflow completes first, then the deploy workflow starts automatically afterward on the self-hosted runner. Expect to see Login Succeeded and successful pulls for both images in the deploy job's logs.

6

Verify locally and compare against your prediction

docker ps
curl http://localhost:8080/health
start http://localhost:30080

Confirm both containers are running with fresh start times, the health check responds, and the app loads in the browser. Compare the actual output to what was predicted in step 4.

7. Code Review Checklist

8. Post-Coding Quiz

Question 1 of 5

The self-hosted runner service is registered under a Windows account with no Docker permissions. What happens when the deploy job runs?

Docker commands require the running user to have Docker access. Without it, every docker command in the script fails, even though the workflow itself started fine.
Question 2 of 5

Why does deploy_local.ps1 remove the old masker-server and masker-client containers before starting new ones?

Two containers cannot both bind host port 8080 (or 30080) at the same time, so the old container has to be removed before the new one can start on that port.
Question 3 of 5

types: [completed] on a workflow_run trigger fires when the watched workflow finishes. What does "completed" include?

completed fires regardless of outcome. A deploy job that shouldn't run after a failed build needs to explicitly check github.event.workflow_run.conclusion == 'success'.
Question 4 of 5

Why is periodically running docker system prune -f a useful cleanup practice on a self-hosted deployment machine?

Each successful deploy leaves the previous image behind on disk unless it's cleaned up. Left unchecked over many deploys, this steadily fills the disk on the deployment machine.

10. What Breaks If This Knowledge Is Missing?

  • Runner installed under an account without Docker permissions: Every Docker step in the deploy job fails with an access error, even though the workflow itself starts and the runner shows green.
  • Using push instead of workflow_run: The deploy job can fire before the image finishes building and pushing, pulling a stale or nonexistent tag and deploying the wrong version — or none at all.
  • Skipping --password-stdin in favor of a typed password: The login step either hangs waiting for interactive input on a runner with no terminal to answer it, or the token ends up exposed in logs or shell history.

11. What We Learned

Today you learned: CD is a distinct step from CI, a self-hosted runner needs Docker permissions to act on local containers, workflow_run chains a deploy job to a completed build instead of racing it on push, --password-stdin logs in without exposing a secret, and the stop-old/pull-new/start-new sequence is what a safe container swap actually looks like.
