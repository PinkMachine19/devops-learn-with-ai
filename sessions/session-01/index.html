Layer 1 Session 01 Docker Foundations

Container Lifecycle, Bind Mounts, Volumes, and Networks

Every layer in this course — from Kubernetes deployments to CI/CD pipelines to production observability — assumes you already know what a container actually is and how it behaves. This is that starting point. Today you run a single container, watch it live, hand it a folder from your own machine, give it storage that survives its death, and connect two containers so they can find each other by name. No orchestration tools yet — just the raw primitives everything else in DevOps is built on top of.

Estimated time: 90–100 minutes

1. Learning Objectives

  1. 1/5Explain the difference between an image and a container, and run a container with docker run
  2. 2/5Inspect running and stopped containers with docker ps and read their output with docker logs
  3. 3/5Serve live host files into a container using a bind mount
  4. 4/5Create a named volume and prove that data in it survives a container being removed and recreated
  5. 5/5Create a Docker network so two containers can reach each other by name instead of IP

2. Pre-Coding Quiz

Answer before reading the concept. Need 4/5 to proceed.

Question 1 of 5

What is a Docker image, most precisely?

An image is a static, read-only blueprint on disk. It doesn't run on its own — a container is what you get when Docker starts a process from it.
Question 2 of 5

You stop a container without removing it. What happens to it?

Stopping a container only halts its process. The container object itself, and anything written to its own writable layer, still exists until you explicitly run docker rm.
Question 3 of 5

What is the actual effect of -v "$(pwd)/data:/usr/share/nginx/html"?

This is a bind mount: it links an exact host path directly into the container's filesystem, so both sides see the identical files live, with no copying involved.
Question 4 of 5

You remove a MySQL container that was using a named volume, then start a new MySQL container pointed at that same volume. What happens to the data?

A named volume is managed by Docker itself, outside the container's lifecycle. Removing the container never touches the volume's contents.
Question 5 of 5

Two containers are attached to the same user-defined Docker network, lab-net. How can one reach the other?

A user-defined network gives every attached container automatic name-based DNS resolution — no port publishing or IP hunting required, and nothing is exposed outside the network unless you choose to.

3. The Concept — Containers, Storage, and Networking

Why Docker exists

Before containers, "it works on my machine" was a permanent problem: an application depended on a specific OS version, a specific set of libraries, and a specific runtime, and none of that traveled with the code. Docker packages an application together with everything it needs to run into a single portable unit, so the exact same thing runs on a laptop, a CI server, and a production host.

The hierarchy: host, daemon, images, containers, volumes

Everything Docker manages lives inside one background service on your machine, the Docker daemon. The daemon builds and stores images, starts and stops containers from those images, and manages volumes that live on the host's own disk.

Volumes are the one box in this diagram that reaches back outside the daemon: the daemon tracks and mounts them, but the bytes themselves sit on the host's real filesystem, which is exactly why they outlive any single container.

docker run, docker ps, docker logs

docker run -d -p 8080:80 nginx:alpine
docker ps -a
docker logs <container-name-or-id>

docker run pulls the image if it isn't already cached locally, creates a container from it, and starts it — the -d flag runs it detached, in the background, and -p 8080:80 maps host port 8080 to port 80 inside the container. docker ps -a lists every container, running or stopped, and docker logs shows whatever that process has written to stdout and stderr, which is normally the first thing worth checking when a container isn't behaving as expected.

Bind mounts: live host files inside a container

mkdir -p data
echo "<h1>Hello from a bind mount</h1>" > data/index.html
docker run -d -p 8081:80 -v "$(pwd)/data:/usr/share/nginx/html" nginx:alpine

A bind mount points a container's directory directly at a directory on your host. Nothing is copied at container start — the container reads and writes the same files that already exist on the host. Edit data/index.html locally, refresh the browser, and the change is there immediately, with no rebuild step.

Named volumes: storage that outlives the container

docker volume create mysql-data
docker run -d --name mysql-lab \
  -e MYSQL_ROOT_PASSWORD=changeme \
  -v mysql-data:/var/lib/mysql \
  mysql:8

A named volume is different from a bind mount in one important way: Docker creates and owns it, rather than pointing at an existing host folder you manage yourself. The volume's actual files live under Docker's own storage area on the host, but from the container's point of view /var/lib/mysql just behaves like a normal directory that happens to survive container removal.

Networks: containers finding each other by name

docker network create lab-net
docker run -d --name mysql-lab --network lab-net \
  -e MYSQL_ROOT_PASSWORD=changeme \
  -v mysql-data:/var/lib/mysql \
  mysql:8

By default, containers are isolated from one another. Creating a user-defined network and attaching containers to it gives every container on that network automatic DNS: a container can reach another simply by its --name, with no manual IP address lookup and nothing exposed to the outside world unless a port is explicitly published with -p.

Containers are disposable, volumes are not. Treat a container the same way you treat a process: fine to kill, fine to recreate. Only the data explicitly placed in a named volume (or a bind mount) survives that. This one distinction is the foundation for almost every storage decision made later in this course.

4. Lab

Lab objective: Run and inspect a basic container, serve a file via bind mount, create a named volume for MySQL and prove it survives container removal, then connect two containers on a shared network.
1

Verify Docker is installed

docker --version

Confirm you see a version string back. If this fails, install Docker Desktop (or Docker Engine on native Linux/WSL2) before continuing.

2

Run a basic NGINX container

docker run -d -p 8080:80 nginx:alpine

Before opening the browser: predict what you'll see at http://localhost:8080. Now open it and confirm — this is NGINX's built-in default page, coming from inside the container's own ephemeral filesystem.

3

Inspect containers and logs

docker ps -a
docker logs <container-id-or-name>

Note the container's name, status, and mapped ports. Stop it with docker stop <name>, run docker ps -a again, and confirm it still appears — just with a different status.

4

Serve static HTML via bind mount

mkdir -p data
echo "<h1>Hello from a bind mount</h1>" > data/index.html
docker run -d -p 8081:80 -v "$(pwd)/data:/usr/share/nginx/html" nginx:alpine

Visit http://localhost:8081 and confirm you see your own HTML, not the NGINX default page. Edit data/index.html, refresh, and confirm the change appears with no restart.

5

Create a named volume and run MySQL with it

docker volume create mysql-data
docker run -d --name mysql-lab \
  -e MYSQL_ROOT_PASSWORD=changeme \
  -v mysql-data:/var/lib/mysql \
  mysql:8

Give MySQL a few seconds to finish its first-time initialization before connecting. Check docker logs mysql-lab for a "ready for connections" message.

6

Predict, then prove persistence

Before doing anything: write down what you expect to happen to a row you insert if the container is deleted and a fresh one is started against the same volume.

docker exec -it mysql-lab mysql -uroot -pchangeme \
  -e "CREATE DATABASE labdb; \
      CREATE TABLE labdb.notes (msg VARCHAR(50)); \
      INSERT INTO labdb.notes VALUES ('still here');"

docker rm -f mysql-lab

docker run -d --name mysql-lab \
  -e MYSQL_ROOT_PASSWORD=changeme \
  -v mysql-data:/var/lib/mysql \
  mysql:8

docker exec -it mysql-lab mysql -uroot -pchangeme -e "SELECT * FROM labdb.notes;"

Was your prediction right? The row should still be there — the container was fully removed and recreated, but the volume never was.

7

Create a network and recreate MySQL inside it

docker network create lab-net

docker rm -f mysql-lab

docker run -d --name mysql-lab --network lab-net \
  -e MYSQL_ROOT_PASSWORD=changeme \
  -v mysql-data:/var/lib/mysql \
  mysql:8

This MySQL container now exposes no port to your host at all — it doesn't need to, since Session 02's PHP container will reach it by name over lab-net instead.

8. Post-Coding Quiz

Question 1 of 5

You run docker rm -f mysql-lab and then start a brand new container with a different name, mounting the same mysql-data volume. What do you see when you query the old table?

A named volume has no permanent link to the container name that first used it. Any container that mounts mysql-data sees the exact same data on disk.
Question 2 of 5

What is the practical difference between a bind mount and a named volume?

Both persist data outside the container's own writable layer, but a bind mount is anchored to a host path you control, while a named volume's storage location is owned and tracked by Docker.
Question 3 of 5

After running docker network create lab-net and attaching both mysql-lab and a future php-lab container to it with --network lab-net, how does php-lab reach MySQL?

Containers on the same user-defined network get automatic DNS resolution by container name — no port publishing or manual host file edits required.
Question 4 of 5

docker ps with no flags shows nothing, even though you just ran a container. Why?

docker ps alone shows only currently running containers. docker ps -a includes stopped and exited ones too, which is why the lab used -a for inspection.

9. Reflection Questions

  1. Before removing and recreating the MySQL container, did you correctly predict the data would survive? What made you confident either way?
  2. Why do you think Docker chose to make containers disposable by default instead of automatically persisting everything a container writes?
  3. What kind of application data would you deliberately choose not to put in a volume?

10. What Breaks If This Knowledge Is Missing?

  • Skip named volumes entirely: Any container restart, redeploy, or crash silently wipes application data — a database that "randomly loses everything" is almost always this exact mistake.
  • Confuse a bind mount with a volume: Deployments break when a hardcoded host path from a developer's laptop doesn't exist on a server, because bind mounts are not portable the way named volumes are.
  • Skip the network step and rely on published ports between your own containers: Every internal service ends up unnecessarily exposed to the host and possibly the internet, widening the attack surface for no real benefit.

11. What We Learned

Today you learned: images are read-only templates and containers are the disposable running instances of them, docker ps/logs are your primary inspection tools, bind mounts share live host files while named volumes are Docker-managed persistent storage, and a user-defined network gives containers name-based DNS instead of manual IP tracking.
