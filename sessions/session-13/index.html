Layer 5 Session 13 Release Strategies — Gate

Canary Deployments (Raw Kubernetes, Helm, and Terraform)

Session 12 added liveness, readiness, and startup probes, plus an HorizontalPodAutoscaler that reacts to load on its own. Those probes did more than keep pods alive — they gave the cluster an honest signal about whether a pod is actually healthy. Canary deployments spend that signal: instead of cutting all traffic to a new version at once like blue-green did in Session 11, a canary release sends a small, deliberate slice of real traffic to the new version first, and only grows that slice once the probes and the numbers say it is safe. This session builds the same canary rollout three times — raw Kubernetes manifests, a Helm chart pair, and Terraform-orchestrated Helm — so the underlying mechanism (NGINX Ingress weighted routing) stays visible under three different layers of tooling.

Estimated time: 70–85 minutes · Flow: Pre-quiz → Concept → Lab → Commit → Post-quiz

1. Learning Objectives

  1. 1/6Explain how a canary release differs from the blue-green cutover built in Session 11

  3. 3/6Build the identical canary rollout with raw Kubernetes YAML, a Helm chart pair, and Terraform-orchestrated Helm
  4. 4/6Trace a canary-weight value from a Terraform variable through a Helm value into an Ingress annotation
  5. 5/6Ramp traffic from 10% → 25% → 50% → 100% and verify the split with real requests, not guesses
  6. 6/6Roll back a canary safely by zeroing its weight or removing its Ingress

2. Pre-Coding Quiz

Answer before reading the concept. Need 4/5 to proceed.

Question 1 of 5

What is the core difference between a blue-green cutover and a canary release?

Blue-green keeps two full environments and cuts all traffic between them instantly. Canary keeps both versions live and grows the new version's traffic share step by step.
Question 2 of 5

How many Ingress objects does a typical NGINX canary setup use?

NGINX merges two separate Ingress objects that share the same host: one plain (stable) and one carrying the canary and canary-weight annotations.
Question 3 of 5

The canary Ingress has canary-weight set to 20. What percentage does the stable Ingress receive?

The stable Ingress carries no weight annotation at all. NGINX treats it as the default, and canary-weight subtracts from that default.
Question 4 of 5

Why do the two Helm charts (diner-stable, diner-canary) need distinct release names and Ingress metadata.name values?

Helm records which release owns which cluster objects. Two releases claiming the same object name collide, even though NGINX is happy to merge routes that share a host.
Question 5 of 5

In the Terraform version, canary_weight is passed through templatefile() into a Helm values file. What must stay true for the annotation to actually render?

A name mismatch between canary_weight, canaryWeight, and {{ .Values.canaryWeight }} anywhere along that chain causes the annotation to render empty, with no error raised.

3. The Concept — Gradual Traffic Shifting, Three Ways

Why canary instead of blue-green every time

Blue-green answers "how do I cut over instantly and roll back instantly." Canary answers a different question: "how do I limit the blast radius of a bug that only shows up under real production traffic." Health probes from Session 12 make canary trustworthy — readiness probes keep an unhealthy canary pod out of rotation automatically, so a bad canary version quietly removes itself from the traffic split rather than serving errors to the users routed to it.

Approach 1: Raw Kubernetes

The rawest version of a canary is two Ingress objects, sharing a host, differentiated by an annotation. Everything else — Deployments, Services, ConfigMaps for distinct HTML per version — is identical in shape to what Session 11 already built for blue-green; only the routing layer changes. 

# ingress-stable.yaml — no weight, treated as the default
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: diner-ingress
  namespace: diner-lab
spec:
  ingressClassName: nginx
  rules:
  - host: diner.local
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: diner-stable-svc
            port:
              number: 80
# ingress-canary.yaml — annotated, carries the weight
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: diner-ingress-canary
  namespace: diner-lab
  annotations:
    nginx.ingress.kubernetes.io/canary: "true"
    nginx.ingress.kubernetes.io/canary-weight: "10"
spec:
  ingressClassName: nginx
  rules:
  - host: diner.local
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: diner-canary-svc
            port:
              number: 80

Use spec.ingressClassName: nginx rather than the older kubernetes.io/ingress.class annotation — the annotation form is deprecated and current NGINX Ingress controllers warn loudly when they see it.

Approach 2: Helm — two charts, one merged route

Helm packages the stable and canary Deployment/Service/Ingress trio each into their own chart and installs them as two independent releases. The key discipline is naming: both charts must scaffold distinct chart names (diner-stable, diner-canary) and their Ingress templates must set distinct metadata.name values, even though both Ingress objects point at the same host: diner.local so NGINX still merges them. 

helm create diner-stable
helm create diner-canary
# diner-stable values.yaml: replicas: 3, no canary annotations
# diner-canary values.yaml: replicas: 1, canary: "true", canary-weight: "20"

helm install diner-stable ./diner-stable -n diner-lab
helm install diner-canary ./diner-canary -n diner-lab
Common failure mode: if the stable release is deleted or never installed, NGINX has only one Ingress to route to — it does not "fail closed." Setting canary: "false" on the canary Ingress does not disable routing either if the stable Ingress is missing; NGINX simply routes everything to whatever backend remains.

Approach 3: Terraform-orchestrated Helm

Terraform does not replace Helm here — it drives it. Each Helm chart install becomes a helm_release resource, and the canary weight becomes a Terraform variable that flows through templatefile() into a Helm values file. 

# main.tf
terraform {
  required_version = ">= 1.6.0"
  required_providers {
    kubernetes = { source = "hashicorp/kubernetes", version = "~> 2.33" }
    helm       = { source = "hashicorp/helm",       version = "~> 2.15" }
  }
}

provider "kubernetes" { config_path = "~/.kube/config" }
provider "helm" {
  kubernetes { config_path = "~/.kube/config" }
}

resource "helm_release" "diner_stable" {
  name             = "diner-stable"
  chart            = "./helm/diner-stable"
  namespace        = "diner-lab"
  create_namespace = true
  values           = [file("values-stable.yaml")]
}

resource "helm_release" "diner_canary" {
  name             = "diner-canary"
  chart            = "./helm/diner-canary"
  namespace        = "diner-lab"
  create_namespace = true
  values = [
    templatefile("values-canary.tpl", {
      canary_weight = var.canary_weight
    })
  ]
}
# variables.tf
variable "canary_weight" {
  type        = number
  default     = 10
  description = "Percentage of traffic routed to canary"
}

# values-canary.tpl
app:
  name: diner-canary
  replicas: 1

canaryWeight: ${canary_weight}

The Ingress template inside the canary chart then reads {{ .Values.canaryWeight }}. Three names have to line up exactly for this chain to work: the Terraform variable canary_weight, the Helm value key canaryWeight, and the template reference to that same key. A mismatch anywhere in that chain renders the annotation empty with no visible error — NGINX just treats the canary weight as unset. 

terraform init
terraform apply -var='canary_weight=10' -auto-approve
kubectl get ingress -n diner-lab   # both diner-stable and diner-canary should appear

terraform apply -var='canary_weight=25' -auto-approve
terraform apply -var='canary_weight=50' -auto-approve

# confirm Helm actually rendered the annotation
helm get manifest diner-canary -n diner-lab | Select-String canary-weight

Rollback, in all three approaches

Every approach rolls back the same way conceptually: reduce the canary weight to zero, or remove the canary Ingress entirely, and full traffic returns to stable without touching the stable Deployment at all. 

# raw kubernetes
kubectl delete -f ingress-canary.yaml -n diner-lab

# helm
helm rollback diner-canary 0
# or
helm uninstall diner-canary

# terraform
terraform apply -var='canary_weight=0' -auto-approve
# or
terraform destroy -target=helm_release.diner_canary -auto-approve

4. Lab

Lab objective: Deploy the same canary rollout three times — raw Kubernetes, Helm, and Terraform — ramp the canary weight from 10% to 100%, and confirm the traffic split with real requests at every stage.
1

Raw Kubernetes: namespace and ConfigMaps

mkdir phase8-canary
cd phase8-canary
kubectl create namespace diner-lab --dry-run=client -o yaml | kubectl apply -f -
kubectl apply -f cm-stable.yaml
kubectl apply -f cm-canary.yaml

The two ConfigMaps hold different HTML colors (stable blue, canary green) so the traffic split is visible with the naked eye, not just in logs.

2

Deployments, Services, and both Ingress objects

kubectl apply -f deploy-stable.yaml
kubectl apply -f deploy-canary.yaml
kubectl apply -f svc.yaml
kubectl apply -f ingress-stable.yaml
kubectl apply -f ingress-canary.yaml
kubectl get ingress -n diner-lab

Predict before running: with canary-weight set to 10, roughly what fraction of 20 requests to http://diner.local do you expect to hit the green (canary) version? Write your prediction down before the next step.

3

Test and observe the traffic split

for ($i=0; $i -lt 20; $i++) { (Invoke-WebRequest http://diner.local).Content | Select-String "blue|green" }
kubectl logs -l version=canary -n diner-lab --tail=20

Compare the actual green-response count against your prediction. NGINX's weighting is probabilistic per request, not a strict round-robin, so small sample sizes will not land on exactly 10%.

4

Ramp the raw Kubernetes canary weight

kubectl annotate ingress diner-ingress-canary -n diner-lab nginx.ingress.kubernetes.io/canary-weight="25" --overwrite
kubectl annotate ingress diner-ingress-canary -n diner-lab nginx.ingress.kubernetes.io/canary-weight="50" --overwrite
kubectl annotate ingress diner-ingress-canary -n diner-lab nginx.ingress.kubernetes.io/canary-weight="100" --overwrite

Re-run the request loop after each step. At weight 100, every response should come from the canary version even though the stable Deployment is still running untouched.

5

Clean up raw Kubernetes, then repeat with Helm

kubectl delete -f ingress-canary.yaml -f ingress-stable.yaml -f svc.yaml -f deploy-canary.yaml -f deploy-stable.yaml -f cm-canary.yaml -f cm-stable.yaml -n diner-lab

helm create diner-stable
helm create diner-canary
# set image, replicas, ConfigMap + Ingress templates per the Concept section
helm install diner-stable ./diner-stable -n diner-lab
helm install diner-canary ./diner-canary -n diner-lab
kubectl get ingress -n diner-lab -o wide
6

Verify the Helm version, then roll back

kubectl describe ingress diner-canary -n diner-lab
helm rollback diner-canary 0
helm uninstall diner-stable diner-canary -n diner-lab

Stop and think: if diner-stable is uninstalled first while diner-canary is still weighted at 20%, what do you expect NGINX to do with the other 80% of traffic? Confirm your answer with a request loop before moving on.

7

Terraform: initialize and apply at weight 10

mkdir terraform-canary
cd terraform-canary
# add main.tf, variables.tf, outputs.tf, values-stable.yaml, values-canary.tpl per the Concept section
terraform init
terraform apply -var='canary_weight=10' -auto-approve
kubectl get ingress -n diner-lab
8

Ramp with Terraform and verify the rendered annotation

terraform apply -var='canary_weight=25' -auto-approve
terraform apply -var='canary_weight=50' -auto-approve
helm get manifest diner-canary -n diner-lab | Select-String canary-weight

If that command returns nothing, the variable name has drifted somewhere between Terraform, the values template, and the Ingress template — walk the chain from variables.tf to values-canary.tpl to the Ingress template and find the mismatch.

9

Roll back and clean up

terraform apply -var='canary_weight=0' -auto-approve
terraform destroy -auto-approve
kubectl delete ns diner-lab

8. Post-Coding Quiz

Question 1 of 5

The stable Ingress is deleted while the canary Ingress is still weighted at 20%. What actually happens to traffic?

The weight only describes how NGINX splits between two merged Ingress objects. With only one backend left, there is nothing to split against, so it receives all traffic regardless of its stated weight.
Question 2 of 5

Which change is required to raise canary traffic from 10% to 25% in the raw Kubernetes approach?

Traffic weight is purely an annotation on the canary Ingress. Replica count affects how much capacity is behind the canary, but not what share of requests NGINX routes to it.
Question 3 of 5

In the Terraform version, helm get manifest diner-canary | Select-String canary-weight returns nothing. What is the most likely cause?

This is the exact failure mode called out in the Concept section — canary_weight, canaryWeight, and .Values.canaryWeight all have to match exactly, and a drift anywhere renders the annotation empty with no error.
Question 4 of 5

Why does canary deployment specifically benefit from the health probes built in Session 12?

Readiness probes are what make a small canary slice actually safe — a broken canary pod stops receiving traffic on its own rather than serving errors to whatever share of users NGINX routed to it.

10. What Breaks If This Knowledge Is Missing?

  • Believing one Ingress can canary itself: A team that tries to encode a percentage split inside a single Ingress object will hit a wall — NGINX's canary mechanism fundamentally requires two merged Ingress objects, not a field inside one.
  • Skipping the naming discipline in Helm: Reusing identical Ingress metadata.name values across the stable and canary charts causes silent ownership conflicts that are confusing to debug without knowing Helm tracks object ownership per release.
  • Ignoring the Terraform variable chain: Without understanding that canary_weight has to match exactly across three files, a team debugging "the weight isn't changing" could spend hours in the wrong place — checking NGINX logs instead of the values template.
  • Treating stable as always-on: Deleting the stable Ingress without first zeroing the canary weight sends all traffic to an under-provisioned canary Deployment, which is the opposite of the safety canary is meant to provide.

11. What We Learned

Today you learned: canary deployments shift a growing percentage of real traffic to a new version by merging two Ingress objects (stable and canary:true) rather than cutting over all at once, and this exact mechanism can be driven from raw Kubernetes YAML, packaged Helm charts, or Terraform-orchestrated Helm — with the underlying NGINX weighted routing staying identical underneath all three.
