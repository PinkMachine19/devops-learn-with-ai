Layer 2 Session 03 Kubernetes

Deployments, Services, Scaling, Rolling Updates, and Rollback

Session 02 ended with Docker Compose running your whole stack on a single host — one docker compose up, one machine, one point of failure. Kubernetes takes the same containers and spreads the job of keeping them running across a cluster: it restarts what crashes, replaces what you update, and gives you a stable way to reach a set of pods that are constantly being created and destroyed underneath you. Today you deploy an app the Kubernetes way, expose it, scale it, roll it forward, and roll it back.

Estimated time: 55–60 minutes

Flow: Pre-quiz → Concept → Lab → Commit → Post-quiz

2. Pre-Coding Quiz

Answer before reading the concept. Need 4/5 to proceed.

Question 1 of 5

Why does Kubernetes typically manage Pods through a Deployment instead of you creating a Pod directly?

A standalone Pod that crashes is simply gone. A Deployment's ReplicaSet notices the gap between desired and actual count and starts a replacement automatically.
Question 2 of 5

Why do Pods need a Service in front of them instead of clients connecting to Pod IPs directly?

Every time a Pod is created it gets a new IP. A Service gives clients one stable address that keeps working as Pods behind it come and go.
Question 3 of 5

By default, what kind of Service does kubectl expose deployment web --port=80 create?

ClusterIP is the default Service type — it's reachable only from inside the cluster unless you explicitly ask for NodePort or LoadBalancer.
Question 4 of 5

You run kubectl scale deployment web --replicas=3 when one Pod is already running. What happens to that existing Pod?

Scaling only adds or removes Pods to close the gap with the desired count. The existing Pod isn't touched at all.
Question 5 of 5

What does a rolling update do differently from just deleting all Pods and creating new ones at once?

A rolling update swaps Pods a few at a time, keeping enough old Pods running to avoid a moment with zero available replicas.

3. The Concept

Deployment, ReplicaSet, Pod — why the extra layers

A Pod is the smallest thing Kubernetes runs — one or more containers sharing a network namespace. You almost never create a Pod directly, because a bare Pod that dies is simply gone. Instead you create a Deployment, which describes the Pod template and how many replicas you want. The Deployment creates and owns a ReplicaSet, and the ReplicaSet is what actually creates and watches the Pods, continuously making sure the number running matches the number you asked for. 

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  labels:
    app: web
spec:
  replicas: 1
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: nginx
          image: nginx:1.25
          ports:
            - containerPort: 80

The selector.matchLabels block is what ties the Deployment to the Pods it manages — it has to match the labels on template.metadata.labels exactly, or the Deployment won't recognize its own Pods.

Desired state reconciliation

Kubernetes controllers don't run your command once and stop watching. A Deployment continuously compares the replica count you declared (the desired state) against what's actually running (the actual state). If a Pod crashes, gets evicted, or is deleted by hand, the controller notices the mismatch on its next reconcile loop and starts a replacement — no human has to notice or react. This is the same loop that makes scaling and rolling updates work: you change the desired state, and the controller drives reality toward it.

Services and stable networking

Every Pod gets its own IP address, but that IP is not durable — it disappears the moment the Pod is replaced, whether by a crash, a scale-down, or a rolling update. A Service solves this by giving you one stable virtual IP and DNS name that always routes traffic to whichever Pods currently match its label selector, regardless of how many times those Pods have been replaced underneath. 

apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  selector:
    app: web
  ports:
    - port: 80
      targetPort: 80
  type: ClusterIP

ClusterIP (the default) is reachable only from inside the cluster — other Pods can reach it, but your laptop's browser can't. NodePort additionally opens a fixed port on every cluster node, so traffic from outside the cluster can reach the Service too. For local development, kubectl port-forward gives you a third option: a temporary tunnel from a local port on your machine straight to the Service, without changing the Service's type at all.

kubectl scale

kubectl scale deployment web --replicas=3

This edits the Deployment's desired replica count. The ReplicaSet picks up the change on its next reconcile pass and creates however many new Pods are needed to close the gap — it does not touch, rename, or restart any Pod that's already running and healthy.

How a rolling update works

A Deployment's default update strategy is RollingUpdate. When you change the Pod template — most commonly the container image — the Deployment creates a new ReplicaSet for the new template and gradually shifts Pods from the old ReplicaSet to the new one. Two settings control the pace: 

spec:
  strategy:
    rollingUpdate:
      maxSurge: 25%        # how many extra Pods can exist above the desired count
      maxUnavailable: 25%  # how many Pods can be unavailable at once

maxSurge allows the rollout to briefly run slightly more Pods than requested so it can start new ones before killing old ones. maxUnavailable caps how many Pods can be down for capacity at once. Together they mean a rollout never has zero working Pods — it trades old Pods for new ones a few at a time, not all at once. 

kubectl set image deployment web nginx=nginx:1.25
kubectl rollout status deployment/web

kubectl rollout undo and rollout history

Every change to a Deployment's Pod template is recorded as a new revision. If a rollout turns out to be broken, kubectl rollout undo deployment/web re-applies the previous revision's spec, triggering another rolling update — this time back toward the last known-good version. kubectl rollout history deployment/web lists the recorded revisions so you can see what changed and when. 

kubectl rollout history deployment/web
kubectl rollout undo deployment/web

4. Lab

Lab objective: Deploy nginx as a Deployment, expose it with a Service, reach it locally, then scale it, roll it forward to a new image version, and roll it back.
1

Verify your cluster is up

If you're using Docker Desktop, enable Kubernetes in its settings and wait for the green "running" indicator. Then confirm from the CLI:

kubectl cluster-info
kubectl get nodes

You should see a control plane URL and at least one node in Ready status.

2

Create the Deployment

Either save the deployment.yaml from Section 3 and apply it, or create the same thing imperatively:

kubectl create deployment web --image=nginx
3

View the Pods

kubectl get pods

Confirm one Pod for web shows STATUS: Running.

4

Expose the Deployment as a Service

kubectl expose deployment web --port=80 --target-port=80

Then verify it exists:

kubectl get services

You should see a web Service with TYPE: ClusterIP.

5

Access it locally with port-forward

kubectl port-forward service/web 8080:80

Leave that running and open http://localhost:8080 in a browser — you should see the default nginx welcome page. Stop the port-forward with Ctrl+C when you're done checking.

6

Check the current Deployment

kubectl get deploy web

Note the current REPLICAS column — it should read 1.

Stop and predict: before running the next command, write down an answer — after kubectl scale deployment web --replicas=3, will kubectl get pods show the existing Pod under a new name, or will it keep its current name while two new Pods appear alongside it?
7

Scale to 3 replicas

kubectl scale deployment web --replicas=3
kubectl get pods

Check your prediction: the original Pod keeps its exact name, and two additional Pods appear with their own generated suffixes.

8

Trigger a rolling update

kubectl set image deployment web nginx=nginx:1.25

This changes the container image in the Pod template, which starts a new ReplicaSet and begins the rollout.

9

Watch the rollout status

kubectl rollout status deployment/web

It streams progress until it prints something like deployment "web" successfully rolled out.

10

Verify all Pods run the new version

kubectl describe pods | grep Image

Every line should now show nginx:1.25.

11

Roll back

kubectl rollout undo deployment/web
kubectl rollout status deployment/web

Re-run the describe | grep Image command from the previous step — the Pods should be back on the original image tag.

12

Scale back down and clean up

kubectl scale deployment web --replicas=1
kubectl delete service web
kubectl delete deployment web

8. Post-Coding Quiz

Question 1 of 5

A Deployment's selector.matchLabels doesn't match the labels on its own Pod template. What happens?

The selector must match the Pod template's labels — Kubernetes validates this at apply time and rejects manifests where they don't line up.
Question 2 of 5

After kubectl rollout undo deployment/web, what actually happens under the hood?

Undo isn't a special-case operation — it triggers a normal rolling update, just targeting the previous revision instead of a newly specified one.
Question 3 of 5

Why can't a client just hard-code a Pod's IP address instead of using a Service?

Whatever hard-coded the old Pod IP breaks the next time that Pod restarts and gets a new one — this is exactly what Services exist to prevent.
Question 4 of 5

You need this Service reachable from a browser outside the cluster, without using port-forward. Which Service type do you switch to?

NodePort opens a fixed port on every node, making the Service reachable from outside the cluster without any port-forwarding session.

10. What Breaks If This Knowledge Is Missing?

  • Creating bare Pods instead of a Deployment: a crashed Pod stays dead — nothing notices and nothing replaces it, so an outage that should self-heal in seconds instead needs a human to notice and intervene.
  • Hard-coding a Pod IP instead of using a Service: the connection works until the very next time that Pod restarts, at which point it silently starts failing for a reason that isn't obvious from the error message.
  • Mismatched selector.matchLabels and template labels: the manifest fails validation, or worse, a Deployment ends up "managing" Pods that don't actually belong to it.
  • Not understanding maxUnavailable during a rollout: a rollout can be assumed to be zero-downtime when it isn't actually configured that way, leading to real user-facing errors during a routine deploy.
  • Not knowing rollout undo exists: a bad image gets manually redeployed with the old tag under time pressure, instead of a one-line command that reuses Kubernetes' own revision history.

11. What We Learned

Today you learned: a Deployment manages a ReplicaSet which manages Pods, a Service gives Pods a stable network identity that survives Pod replacement, kubectl scale changes replica count without touching existing Pods, a rolling update replaces Pods gradually to avoid downtime, and kubectl rollout undo reverses a bad rollout using Kubernetes' own revision history.
