Capstone: Building the Text Masker App

Session 15 closed out the landscape survey and the Layer 6 gate check — the course now moves from talking about tools to actually shipping something. Today's build is the "Text Masker" app: a tiny two-part application made of a Node/Express API that obfuscates text with leet-speak substitutions, and a static HTML/JS client that calls it. Both halves get containerized with Docker from scratch. This exact app carries forward through the next several sessions — automated with a CI pipeline, then deployed to local Docker, then to a local Kubernetes cluster — so getting the plumbing right today pays off repeatedly.

2. Pre-Coding Quiz

Answer before reading the concept. Need 4/5 to proceed.

Question 1 of 5

What does calling app.listen(PORT) in an Express server actually do?

app.listen opens a socket on that port and keeps the Node process alive indefinitely so it can accept and respond to incoming connections.
Question 2 of 5

Why is POST with a JSON body preferred over GET with a query string for sending text to /mask?

Special characters in a URL need percent-encoding and tend to end up in server access logs and browser history; a POST body avoids both issues.
Question 3 of 5

What is a Dockerfile?

A Dockerfile is a build recipe — base image, install steps, files to copy, and a startup command — that produces the same image on any machine with Docker.
Question 4 of 5

Why does this lab build the client and server as two separate Docker images instead of one?

The server runs Node and the client is served by Nginx as static files — keeping them separate lets each be built, deployed, and scaled on its own.
Question 5 of 5

What problem does CORS solve here?

The browser blocks a page from reading a cross-origin response unless the server explicitly allows it via a CORS header — that's exactly the situation between ports 30080 and 8080.

3. The Concept — Two Small Programs, One HTTP Conversation

Architecture of the two-part app

The Text Masker app is deliberately small: a Node/Express API on one side, and a static HTML/JS page on the other. The client never touches the masking logic directly — it sends the user's text to the server over HTTP and displays whatever comes back. This split mirrors real production systems far more than a single monolithic script would, and it's the shape this capstone keeps for the rest of the course: the same two components get automated, containerized differently, and eventually deployed to a cluster, but the client/server boundary never moves.

The masking API: routes and JSON body handling

The server exposes three routes: a health check, a GET version of the masking endpoint kept mostly for convenience and comparison, and the POST version the client actually uses. express.json() is registered as middleware so that any POST body sent as JSON is parsed into req.body automatically, before the route handler ever runs. 

const express = require("express");

const app = express();
const port = process.env.PORT || 8080;

app.use(express.json()); // parse JSON bodies

// Leet/confusables map — a small set of substitute characters per letter
const MAP = {
  a: ["A", "4", "@"], b: ["8", "|3"], c: ["(", "<"],
  e: ["3", "€"], i: ["1", "!", "|"], o: ["0", "()"],
  s: ["5", "$"], t: ["7", "+"]
  // ...remaining letters follow the same pattern
};

function maskLetter(ch) {
  if (!ch) return "";
  const opts = MAP[ch.toLowerCase()];
  if (opts && opts.length) return opts[Math.floor(Math.random() * opts.length)];
  return ch;
}

// Backslash-escape mode: a leading "\" masks only the character after it
function maskText(text) {
  let out = "";
  const chars = Array.from(text);
  for (let i = 0; i < chars.length; i++) {
    const ch = chars[i];
    if (ch === "\\") {
      if (i + 1 < chars.length) { i++; out += maskLetter(chars[i]); }
    } else {
      out += ch;
    }
  }
  return out;
}

app.get("/health", (_req, res) => res.json({ ok: true }));

// GET convenience route — works, but requires URL-encoding for backslashes
app.get("/mask", (req, res) => {
  res.set("Access-Control-Allow-Origin", "*");
  const text = typeof req.query.text === "string" ? req.query.text : "";
  const versions = Math.max(1, Math.min(20, parseInt(req.query.versions || "3", 10) || 3));
  const outputs = Array.from({ length: versions }, () => maskText(text));
  res.json({ input: text, versions, outputs, method: "GET" });
});

// POST route — the one the client actually calls
app.post("/mask", (req, res) => {
  res.set("Access-Control-Allow-Origin", "*");
  const text = typeof req.body.text === "string" ? req.body.text : "";
  const versions = Math.max(1, Math.min(20, parseInt(req.body.versions ?? 3, 10) || 3));
  const outputs = Array.from({ length: versions }, () => maskText(text));
  res.json({ input: text, versions, outputs, method: "POST" });
});

app.listen(port, () => console.log(`Masker API running on ${port}`));

Notice that maskLetter picks randomly from a small list of substitute characters, so calling the API twice with the same input produces two different-looking masked strings. The versions parameter controls how many randomized outputs come back in a single response, capped between 1 and 20 so a careless request can't ask the server to generate an unbounded amount of output.

Why POST is preferred here

Both a GET and a POST route exist for /mask, but the client only ever calls the POST one. Text data — especially anything containing the backslash-escape syntax this API supports — gets awkward fast in a URL: special characters need percent-encoding, the URL length has practical limits, and query strings tend to get written to server access logs verbatim. A JSON body sidesteps all of that; the exact characters the user typed travel to the server untouched.

CORS between the two container ports

The client is served from one container on port 30080, and the API runs in a different container on port 8080. Even though both run on the same machine during local development, the browser treats them as two separate origins because the port differs. Without an explicit Access-Control-Allow-Origin header on the server's response, the browser would block the client's JavaScript from reading that response at all — the request would still reach the server, but the fetch call in the browser would fail. Setting that header on both the GET and POST handlers is what makes the cross-origin fetch work.

Dockerfile structure: a Node API vs. an Nginx-served static client

The server needs a JavaScript runtime, so its Dockerfile starts from a Node base image, installs dependencies, copies in the source, and runs node server.js as its startup command: 

FROM node:20-alpine
WORKDIR /app
COPY package*.json ./
RUN npm install --omit=dev
COPY . .
EXPOSE 8080
CMD ["node", "server.js"]

Copying package*.json before the rest of the source and running npm install in its own layer matters for build speed: Docker caches each instruction as a layer, and as long as the package files haven't changed, later builds can reuse the cached install step instead of re-downloading every dependency.

The client has no server-side logic at all — it's plain HTML, CSS, and JavaScript that only needs a web server to host the files. Its Dockerfile starts from an Nginx base image and simply copies the static files into Nginx's default web root: 

FROM nginx:alpine
COPY . /usr/share/nginx/html
EXPOSE 80

No Node install, no build step, no dependency layer — Nginx already knows how to serve static files the moment the container starts.

The client: a fetch call to the server

async function mask() {
  const text = document.getElementById("inputText").value;
  const res = await fetch("http://localhost:8080/mask", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ text, versions: 3 })
  });
  const data = await res.json();
  document.getElementById("output").textContent = (data.outputs || []).join("\n");
}

This is the entire client-side logic: read the input box, POST it to the server as JSON, wait for the JSON response, and print the outputs array to the page. Everything interesting — the actual masking — happens on the server.

4. Lab

Lab objective: Build the Text Masker server and client from scratch, containerize each with its own Dockerfile, run both locally, and confirm the client can successfully mask text through the API.
1

Create the project folders

mkdir masker-lab; cd masker-lab
mkdir server, client

Two top-level folders: one for the API, one for the static client. Each will get its own Dockerfile.

Write the server: server.js, package.json, Dockerfile

Create server/server.js with the Express app shown in the concept section above (health route, GET and POST /mask routes, and app.listen).

Create server/Dockerfile exactly as shown above (Node base image, install, copy, expose 8080, run node server.js).

Build and run the server, then health-check it

docker build -t masker-server .\server
docker rm -f masker-server 2>$null
docker run -d --name masker-server -p 8080:8080 masker-server
curl.exe http://localhost:8080/health

Predict, then observe: before running the curl command, write down what you expect the response body to look like. Then run it and compare — it should return {"ok":true}.

Now test the POST route with a real payload:

$body = @{ text = "hide these words"; versions = 2 } | ConvertTo-Json
curl.exe -X POST "http://localhost:8080/mask" -H "Content-Type: application/json" --data $body

Predict how many masked strings the response will contain before you run it — the answer should match the versions value sent in the body.

6

Smoke test in the browser

Type any text into the input box and click "Mask It". Before clicking, predict whether you expect three masked lines or one — the client requests versions: 3 in its fetch call. You should see three randomized masked lines appear in the output box. If nothing appears, open the browser console first — a CORS or network error will show up there.

Troubleshooting quickies:
  • Empty reply from server: check docker logs masker-server for a startup error.
  • Import/module errors: confirm the server's package.json does not contain "type": "module" — this server is written as CommonJS.
  • Express not found: rebuild without the cache: docker build --no-cache -t masker-server .\server.
  • Port already in use: run with a different host port, e.g. -p 18080:8080, and call http://localhost:18080 instead.
  • Blank output with a CORS error in the console: confirm both /mask handlers set Access-Control-Allow-Origin before responding.

8. Post-Coding Quiz

Question 1 of 5

A client requests { text: "hi", versions: 5 }. What should the response's outputs array contain?

maskText is called once per requested version, and maskLetter picks randomly each time, so each entry in the outputs array can look different even for identical input.
Question 2 of 5

In the input string "\\a\\b c", what does the backslash-escape mode do to the space and the letter "c"?

maskText only masks a character when the character immediately before it is a backslash; anything without a preceding backslash, including the space and the trailing "c" here, passes through as-is.
Question 3 of 5

If the server's Access-Control-Allow-Origin header were removed entirely, what would happen?

CORS is enforced by the browser after the response arrives, not by the server refusing the request — the server still processes it, but the fetch call in the client's JavaScript throws instead of returning data.
Question 4 of 5

Why does the server's Dockerfile copy package*.json and run npm install before copying the rest of the source code?

Docker caches each build instruction as a layer; if the package files are unchanged since the last build, Docker skips re-running npm install and reuses the cached layer, speeding up rebuilds.

10. What Breaks If This Knowledge Is Missing?

  • Skipping the CORS header: the app looks completely broken from the browser's perspective — the server logs show successful requests, but the client's fetch call throws and nothing ever renders, which is confusing to debug without understanding CORS.
  • Using GET with a query string instead of POST with JSON: any text containing a backslash, space, or other special character gets mangled by URL-encoding, silently producing wrong results instead of an obvious error.
  • Not understanding Docker layer caching: every single build re-downloads all dependencies from scratch, turning a two-second rebuild into a multi-minute one and making local iteration painfully slow.

11. What We Learned

Today you learned: Express routes match a request's method and path to a handler, app.listen keeps the server process alive, POST with a JSON body is the right choice for sending text data, CORS is required whenever client and server run on different origins, and a Dockerfile is a repeatable recipe that builds a runnable image without a local language runtime installed.
