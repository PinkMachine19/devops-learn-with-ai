Layer 4 Session 10 Ingress & TLS

TLS with cert-manager

Session 09 got diner.local (or an sslip.io hostname) routing to the app over plain HTTP. That's fine for a lab, but every production Ingress needs HTTPS. Today the same hostname gets a certificate two ways: first a manually generated, self-signed certificate wired in by hand, then a trusted, auto-renewing certificate issued by Let's Encrypt through cert-manager — with no manual renewal step ever again.

Estimated time: 50–60 minutes  ·  Flow: Pre-quiz → Concept → Lab → Commit → Post-quiz

1. Learning Objectives

  1. 1/6Explain TLS termination: the Ingress decrypts HTTPS and forwards plain HTTP to the Pod
  2. 2/6Generate a self-signed certificate with OpenSSL and wire it into an Ingress manually as a kubernetes.io/tls Secret
  3. 3/6Install cert-manager and create a ClusterIssuer for Let's Encrypt
  4. 4/6Request a Certificate resource and confirm it reaches the Ready state
  5. 5/6Explain the HTTP-01 challenge cert-manager uses to prove domain ownership to Let's Encrypt
  6. 6/6Force all traffic to HTTPS using the force-ssl-redirect annotation

2. Pre-Coding Quiz

Answer before reading the concept. Need 4/5 to proceed.

Question 1 of 5

When TLS terminates at the Ingress, what protocol does traffic use between the Ingress controller and the backend Pod?

Termination means the Ingress does the decrypting. Unless the setup explicitly re-encrypts (end-to-end TLS), the hop from Ingress to Pod is ordinary HTTP.
Question 2 of 5

Why does a browser show a warning for a self-signed certificate but not for one from Let's Encrypt?

Both types encrypt traffic equally well. The warning is about trust: browsers ship a list of trusted CAs, and Let's Encrypt is on it — a self-signed cert has no such backing.
Question 3 of 5

What is a ClusterIssuer for?

A ClusterIssuer holds the account and ACME server details once; any namespace's Certificate resource can reference it instead of repeating that setup per app.
Question 4 of 5

How does the HTTP-01 challenge prove domain ownership to Let's Encrypt?

cert-manager places a token at a well-known path via the Ingress. Let's Encrypt fetches that path over the actual domain — if the correct token comes back, ownership is proven.
Question 5 of 5

Both the manual and cert-manager approaches ultimately store the certificate as what kind of object?

Whether created by hand with kubectl create secret tls or automatically by cert-manager, the cert and key end up as a standard TLS Secret the Ingress references by name.

3. The Concept — From Plain HTTP to Automated HTTPS

TLS termination: where encryption actually ends

"TLS termination" means the Ingress controller is the component that decrypts incoming HTTPS traffic. It holds the certificate and private key, performs the TLS handshake with the client, and then forwards the now-decrypted request to the backend Pod as plain HTTP over the cluster's internal network. This is why only the Ingress needs a certificate at all — the app itself never has to know TLS exists.

Stage 1: a manual, self-signed certificate

Before reaching for automation, it helps to see every piece TLS on Ingress actually requires, by doing it by hand once. 

openssl req -x509 -nodes -days 365 -newkey rsa:2048 \
  -keyout cert.key -out cert.crt \
  -subj "/CN=diner.127.0.0.1.sslip.io"

This produces a certificate and private key that are cryptographically valid but signed only by themselves — no browser trusts them by default. Store them as a Kubernetes Secret: 

kubectl create secret tls diner-tls \
  --cert=cert.crt --key=cert.key \
  -n diner-lab

Then reference that Secret from the Ingress's spec.tls:

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: diner-ingress
  namespace: diner-lab
  annotations:
    nginx.ingress.kubernetes.io/force-ssl-redirect: "true"
spec:
  ingressClassName: nginx
  tls:
    - hosts:
        - diner.127.0.0.1.sslip.io
      secretName: diner-tls
  rules:
    - host: diner.127.0.0.1.sslip.io
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: diner-a-svc
                port: { number: 80 }

spec.tls is the piece that turns on HTTPS for this Ingress: it lists which hostnames the certificate covers and which Secret holds the certificate and key. Test it with: 

curl -vk https://diner.127.0.0.1.sslip.io

The -k flag tells curl to skip certificate trust verification — necessary here specifically because the certificate is self-signed. The handshake still succeeds and the response still comes back encrypted; only the trust chain is missing.

The manual approach doesn't scale

This certificate expires in 365 days and nothing renews it automatically. A production system with dozens of hostnames, each needing its own trusted certificate renewed before expiry, cannot rely on someone remembering to re-run OpenSSL. That's the gap cert-manager closes.

Stage 2: cert-manager and Let's Encrypt

Install cert-manager the same way any other controller gets installed — via Helm:

helm repo add jetstack https://charts.jetstack.io
helm repo update

helm install cert-manager jetstack/cert-manager \
  --namespace cert-manager --create-namespace \
  --set installCRDs=true

installCRDs=true matters: cert-manager defines new Kubernetes object types — ClusterIssuer and Certificate — and those types have to exist before you can create instances of them.

ClusterIssuer: configuring the CA once

apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: letsencrypt-prod
spec:
  acme:
    server: https://acme-v02.api.letsencrypt.org/directory
    email: you@example.com
    privateKeySecretRef:
      name: letsencrypt-prod-key
    solvers:
      - http01:
          ingress:
            ingressClassName: nginx

solvers.http01 tells cert-manager to prove domain ownership using the HTTP-01 challenge: it will temporarily configure the Ingress to serve a token at a well-known path, and Let's Encrypt will fetch that path to confirm control of the hostname before issuing anything.

Requesting the certificate

apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: diner-cert
  namespace: diner-lab
spec:
  secretName: diner-tls
  issuerRef:
    name: letsencrypt-prod
    kind: ClusterIssuer
  dnsNames:
    - diner.127.0.0.1.sslip.io

Once applied, cert-manager runs the entire ACME conversation automatically: request, challenge, verification, issuance — and writes the result into the diner-tls Secret, the exact same kind of object created manually in Stage 1. 

kubectl describe certificate diner-cert -n diner-lab

A Ready: True condition in the output means the certificate was issued successfully and cert-manager will also handle renewal automatically, well before the certificate's expiry date.

Forcing HTTPS-only traffic

metadata:
  annotations:
    nginx.ingress.kubernetes.io/force-ssl-redirect: "true"

With this annotation, any request that arrives over plain HTTP gets a redirect response pointing at the HTTPS version of the same URL instead of being served directly — the app becomes unreachable over unencrypted HTTP entirely.

sslip.io note: Let's Encrypt's HTTP-01 challenge needs to reach your Ingress over the public internet on port 80. This works cleanly when the cluster has a real externally reachable IP; on a fully local cluster, the manual self-signed approach from Stage 1 is what you can actually complete end-to-end, while the cert-manager steps in Stage 2 should be understood and configured correctly even if the final ACME handshake can't complete from a private network.

4. Lab

Lab objective: Serve the diner app over HTTPS first with a manually generated self-signed certificate, then install cert-manager, configure a ClusterIssuer, and request a real certificate for the same hostname.
1

Generate a self-signed certificate

openssl req -x509 -nodes -days 365 -newkey rsa:2048 \
  -keyout cert.key -out cert.crt \
  -subj "/CN=diner.127.0.0.1.sslip.io"

Predict before running: will a browser trust this certificate without any warning? Confirm your answer once you test in step 3.

2

Create the TLS Secret and wire it into the Ingress

kubectl create secret tls diner-tls \
  --cert=cert.crt --key=cert.key -n diner-lab

Update ingress.yaml from Session 09 to add the spec.tls block and the force-ssl-redirect annotation shown in the Concept section, then apply it:

kubectl apply -f ingress.yaml -n diner-lab
3

Test HTTPS locally

curl -vk https://diner.127.0.0.1.sslip.io

Confirm the TLS handshake succeeds and the app's response comes back. Then try a plain HTTP request and confirm it redirects instead of serving content directly, proving force-ssl-redirect is active.

4

Install cert-manager

helm repo add jetstack https://charts.jetstack.io
helm repo update
helm install cert-manager jetstack/cert-manager \
  --namespace cert-manager --create-namespace \
  --set installCRDs=true

kubectl get pods -n cert-manager

Confirm all three cert-manager pods (controller, webhook, cainjector) reach Running before continuing.

5

Create a ClusterIssuer and request a certificate

Apply the ClusterIssuer and Certificate manifests from the Concept section, substituting your own contact email.

kubectl apply -f cluster-issuer.yaml
kubectl apply -f certificate.yaml

kubectl describe certificate diner-cert -n diner-lab

Stop and think: before checking the output, predict what condition you expect to see if the ACME challenge succeeds versus if it can't reach your cluster from the public internet. Read the Events section of the describe output either way — it explains exactly what cert-manager attempted.

8. Post-Coding Quiz

Question 1 of 5

Why did testing the self-signed certificate require curl's -k flag?

-k skips certificate verification. The handshake and encryption work fine; only the chain of trust back to a recognized CA is missing for a self-signed cert.
Question 2 of 5

What does cert-manager write to a Kubernetes Secret once a Certificate becomes Ready?

The Secret named in spec.secretName ends up holding tls.crt and tls.key, in the exact same shape a manually created kubernetes.io/tls Secret would have.
Question 3 of 5

What specifically does the HTTP-01 solver require to succeed?

The HTTP-01 challenge is only satisfied if Let's Encrypt can actually fetch the challenge token from the domain over the public internet — a private-only cluster cannot complete it.
Question 4 of 5

Why is a ClusterIssuer defined once and referenced by many Certificate resources, instead of repeating the ACME configuration in each Certificate?

The ClusterIssuer centralizes the "how to talk to this CA" configuration once, cluster-wide, so each Certificate only needs to say what hostname it wants and which issuer to use.
Question 5 of 5

Session 11 will focus on:

Session 11 introduces blue-green deployments: two live versions of the app running side by side, with traffic switched from one to the other as a deployment strategy.

9. Reflection Questions

  1. Before running the ClusterIssuer and Certificate manifests, did you correctly predict whether the HTTP-01 challenge could complete from your specific network setup? What determined the answer?
  2. What operational burden does cert-manager remove that the manual self-signed approach from Stage 1 leaves entirely on a human?
  3. If force-ssl-redirect had been left off, what would a user typing the plain http:// URL actually experience?

10. What Breaks If This Knowledge Is Missing?

  • Skipping force-ssl-redirect: the app remains reachable over unencrypted HTTP even after TLS is configured, silently defeating the purpose of adding a certificate at all.
  • Never automating renewal: a manually issued certificate expiring unnoticed causes an outage — every client suddenly sees a broken TLS handshake with no code change involved.
  • Mismatched secretName between spec.tls and the Certificate resource: cert-manager issues a valid certificate into a Secret the Ingress never actually reads, so HTTPS still fails despite everything appearing to succeed individually.

11. What We Learned

Today you learned: TLS terminates at the Ingress, a self-signed certificate proves the mechanics but isn't trusted by browsers, cert-manager automates the entire request-challenge-issue-renew cycle with Let's Encrypt through a ClusterIssuer and Certificate resource, and force-ssl-redirect ensures HTTP is never actually served.
