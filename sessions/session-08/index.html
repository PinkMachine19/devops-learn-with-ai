Layer 3 Session 08 Gate Packaging & Infrastructure as Code

Terraform with Kubernetes and Helm Providers

Session 07 proved Terraform can provision a network and a bare endpoint. Session 06 proved Helm can package and release an application into a cluster that already exists. This session closes Layer 3 by pointing Terraform directly at Kubernetes and Helm: one terraform apply creates a namespace and installs a Helm release into it, tracked in the same state file as any other resource. This is the Layer 3 gate — passing it confirms you can drive both infrastructure and application deployment from a single tool.

Estimated time: 55–65 minutes

Pre-quiz → Concept → Lab → Commit → Post-quiz

  1. 1/5Configure both the kubernetes and helm providers in a single Terraform config

2. Pre-Coding Quiz

Answer before reading the concept. Need 4/5 to proceed.

Question 1 of 5

Can a single Terraform configuration use both the kubernetes provider and the helm provider at the same time?

Terraform configs commonly combine multiple providers. Here, kubernetes manages raw objects and helm manages chart releases, both against the same cluster.
Question 2 of 5

What does a helm_release Terraform resource actually correspond to?

helm_release wraps the same install/upgrade behavior as the Helm CLI, but tracked and managed as a Terraform-owned resource in state.
Question 3 of 5

Why is a Terraform-managed Helm release generally considered more reproducible than running helm install manually from a terminal?

Reproducibility comes from the config living in source control and Terraform tracking exactly what it applied — not from any speed or version difference.
Question 4 of 5

What is Terraform "drift," in the context of a namespace or Helm release it manages?

Drift happens when someone or something changes a Terraform-managed resource outside of Terraform — for example, editing a namespace label directly with kubectl.
Question 5 of 5

Why would you refactor namespace + helm_release resources into a reusable module instead of copy-pasting them for dev, stage, and prod?

A module is Terraform's mechanism for reuse — the same resource pattern gets called multiple times with different inputs instead of being duplicated three times over.

3. The Concept — One Control Plane for Infra and Apps

Why point Terraform at Kubernetes and Helm at all

Real applications rarely live on a single VM anymore — they are packaged as containers, deployed on Kubernetes, and released with Helm. Session 06 drove that release step with the Helm CLI directly; session 07 drove infrastructure with Terraform directly. This session merges both under Terraform: the same init → plan → apply → destroy loop now manages a Kubernetes namespace and a Helm release together, producing one consistent, repeatable deployment across environments.

Configuring both providers

terraform {
  required_providers {
    kubernetes = {
      source  = "hashicorp/kubernetes"
      version = "~> 2.27"
    }
    helm = {
      source  = "hashicorp/helm"
      version = "~> 2.13"
    }
  }
}

provider "kubernetes" {
  config_path    = pathexpand("~/.kube/config")
  config_context = "docker-desktop"
}

provider "helm" {
  kubernetes {
    config_path    = pathexpand("~/.kube/config")
    config_context = "docker-desktop"
  }
}

Both providers point at the same cluster through the same kubeconfig, but they operate through separate APIs — kubernetes talks to the Kubernetes API server directly, while helm drives the same install/upgrade logic the Helm CLI uses internally.

A raw Kubernetes resource: the namespace

resource "kubernetes_namespace" "dev" {
  metadata {
    name = "dev"
  }
}

This is the simplest possible proof that the kubernetes provider is correctly authenticated and talking to the right cluster — before layering anything more complex on top, confirm this one resource applies cleanly.

A Helm release as a Terraform resource

resource "helm_release" "nginx" {
  name       = "nginx"
  repository = "https://charts.bitnami.com/bitnami"
  chart      = "nginx"
  version    = "15.0.0"
  namespace  = kubernetes_namespace.dev.metadata[0].name

  values = [
    file("${path.module}/values/dev.yaml")
  ]
}

kubernetes_namespace.dev.metadata[0].name reaches into the namespace resource's computed attributes to reuse its name — the [0] is there because metadata is a Terraform block, which is represented internally as a list with one element. This reference also creates an implicit dependency: Terraform creates the namespace before attempting the Helm release inside it.

The values file works exactly like -f values.yaml on the Helm CLI, just loaded through Terraform's file() function: 

# values/dev.yaml
replicaCount: 2
service:
  type: NodePort
image:
  tag: latest

Helm CLI vs. terraform helm_release

helm install (CLI)              terraform helm_release
──────────────────              ───────────────────────
manual, one cluster at a time    tracked in Terraform state
not versioned as code by itself  lives in version control as HCL
easy to forget what was run      reproducible via plan/apply
                                  works alongside other infra resources

Nothing about the underlying chart changes — the difference is entirely in how the release is declared, tracked, and reproduced.

Drift detection

If someone runs kubectl edit namespace dev or helm upgrade nginx manually outside of Terraform, the cluster no longer matches what Terraform's state file recorded. The next terraform plan compares state against the live cluster and surfaces that mismatch as proposed changes — this is how Terraform-managed infrastructure catches manual, out-of-band edits. 

[ Terraform State ] ---compare---> [ Live Cluster ]
                          |
                    drift found?
                          |
                 terraform plan shows it

Modules: one definition, many environments

Once the namespace-plus-release pattern works for one environment, the next step is extracting it into a module so dev, staging, and production can each call it with different inputs instead of duplicating the resource blocks three times: 

# modules/app/variables.tf
variable "namespace" { type = string }
variable "replica_count" { type = number }

# modules/app/main.tf
resource "kubernetes_namespace" "this" {
  metadata { name = var.namespace }
}

resource "helm_release" "nginx" {
  name       = "nginx"
  repository = "https://charts.bitnami.com/bitnami"
  chart      = "nginx"
  namespace  = kubernetes_namespace.this.metadata[0].name
  set {
    name  = "replicaCount"
    value = var.replica_count
  }
}
# environments/dev/main.tf
module "app" {
  source        = "../../modules/app"
  namespace     = "dev"
  replica_count = 2
}

4. Lab

Lab objective: Use Terraform's kubernetes and helm providers together to create a namespace and install a Helm release into it, verify both in the cluster, then destroy them as one unit.
1

Set up the providers

# versions.tf
terraform {
  required_version = ">= 1.6.0"
  required_providers {
    kubernetes = {
      source  = "hashicorp/kubernetes"
      version = "~> 2.27"
    }
    helm = {
      source  = "hashicorp/helm"
      version = "~> 2.13"
    }
  }
}
# providers.tf
provider "kubernetes" {
  config_path    = pathexpand("~/.kube/config")
  config_context = "docker-desktop"
}

provider "helm" {
  kubernetes {
    config_path    = pathexpand("~/.kube/config")
    config_context = "docker-desktop"
  }
}
terraform init

Predict before running: which two provider plugins do you expect init to download?

2

Create the namespace resource and apply it alone first

# main.tf
resource "kubernetes_namespace" "dev" {
  metadata {
    name = "dev"
  }
}
terraform plan
terraform apply
kubectl get ns dev

Confirm the namespace exists in the cluster before adding the Helm release.

3

Add the values file and the helm_release resource

# values/dev.yaml
replicaCount: 2
service:
  type: NodePort
image:
  tag: latest
# append to main.tf
resource "helm_release" "nginx" {
  name       = "nginx"
  repository = "https://charts.bitnami.com/bitnami"
  chart      = "nginx"
  version    = "15.0.0"
  namespace  = kubernetes_namespace.dev.metadata[0].name

  values = [
    file("${path.module}/values/dev.yaml")
  ]
}
4

Plan and apply, then verify

terraform plan -out=tfplan
terraform apply tfplan

Stop and think: the plan should show the namespace as unchanged (already applied) and only the helm_release as an addition. If it shows the namespace being recreated, something in step 2 was not applied cleanly — check before continuing.

kubectl get ns
kubectl get pods -n dev
helm list -n dev
5

Change a value through Terraform, not through Helm directly

Edit values/dev.yaml to set replicaCount: 3, then run terraform plan again.

Predict before running: will Terraform show the helm_release resource as changed, and will the namespace resource show any change at all?

terraform apply
6

Clean up everything Terraform manages

terraform destroy

Confirm both the Helm release and the namespace are gone:

helm list -n dev
kubectl get ns dev

8. Post-Coding Quiz

Question 1 of 5

Why does the lab apply the kubernetes_namespace resource before adding the helm_release resource, rather than writing both at once from the start?

This is a debugging strategy, not a technical requirement — isolating the simpler resource first makes it much easier to tell which provider is misconfigured if something fails.
Question 2 of 5

After changing values/dev.yaml and reapplying, what does terraform plan show for the kubernetes_namespace.dev resource?

The namespace and the release are independent resources. A values file change only affects the helm_release resource that reads it.
Question 3 of 5

Someone on your team runs helm upgrade nginx manually against the dev namespace, bypassing Terraform. What happens on the next terraform plan?

This is exactly the drift scenario from the concept section — Terraform compares its state against the live release and surfaces the mismatch.
Question 4 of 5

What is the main benefit of extracting the namespace + helm_release pattern into a reusable module?

Reuse is the entire point — one module definition, called three times with different inputs, replaces three near-duplicate copies of the same resource blocks.

9. Reflection Questions

  1. What would you lose by keeping infrastructure in Terraform but continuing to install Helm charts manually with the CLI, outside of Terraform's tracking?
  2. How does the kubernetes_namespace.dev.metadata[0].name reference change how you think about resource dependencies compared to Session 07's docker_network reference?
  3. If you were setting this up for a real team with dev, stage, and prod environments, what would you parameterize in the module beyond just replica_count?

10. What Breaks If This Knowledge Is Missing?

  • Managing the namespace with Terraform but the Helm release manually: the two lifecycles fall out of sync — destroying the namespace with Terraform can strand or orphan a release Terraform never knew about.
  • Hardcoding the namespace name in helm_release instead of referencing the resource: if the namespace name ever changes, the release silently keeps pointing at a namespace that may no longer exist or no longer match.
  • Skipping modules for multi-environment setups: dev, stage, and prod configs drift apart from hand-maintained copies, and a fix applied to one is easy to forget applying to the others.

11. What We Learned

Today you learned: Terraform can configure the kubernetes and helm providers together, manage a namespace and a helm_release as resources in the same state, detect drift when changes happen outside Terraform, and reuse a resource pattern across environments with modules.
