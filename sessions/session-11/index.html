Layer 5 Session 11 Release Strategies

Blue-Green Deployments (Raw Kubernetes, Helm, and Terraform)

Session 10 put a cert-manager certificate in front of the app and gave it a trusted HTTPS address behind an ingress. That address is now permanent — but the thing behind it does not have to be. Today you'll learn how to release a brand-new version of the app onto that same ingress, at that same URL, with zero downtime and an instant undo: blue-green deployment, built three different ways — raw kubectl, Helm, and Terraform — so you can see the same idea survive three different tools.

Estimated time: 65–80 minutes (all three approaches)

Flow: Pre-quiz → Concept → Lab → Commit → Post-quiz

2. Pre-Coding Quiz

Answer before reading the concept. Need 4/5 to proceed.

Question 1 of 5

What best describes a blue-green deployment?

Blue-green keeps two complete, independent copies running side by side. Exactly one receives real traffic at a time, and switching which one is a single atomic action.
Question 2 of 5

In the raw Kubernetes approach, what actually performs the traffic cutover?

The Service's selector decides which pods it routes to. Editing that one label (for example color: blue to color: green) and reapplying the manifest is the entire cutover.
Question 3 of 5

What is the main resource cost of blue-green deployments?

The standby environment has to be fully running and ready at all times to make an instant switch possible, so you pay for its CPU and memory continuously, not just during the cutover.
Question 4 of 5

In the Helm approach, what triggers the switch to the green release?

Helm templates render from values. Changing the activeColor value and running helm upgrade re-renders and reapplies the Service that selects on that color.
Question 5 of 5

In the Terraform approach, what single variable decides which color is live?

active_color feeds a locals map that resolves to the correct Service name, which the ingress backend then points at.

3. The Concept — One Idea, Three Tools

Every approach below solves the exact same problem: run a new version of the app fully side by side with the old one, prove it works, and flip a single switch to send real traffic to it. What changes between approaches is only where that switch lives and how it gets flipped.

Approach 1: Raw Kubernetes

With plain manifests, blue and green are two ordinary Deployments that happen to share an app label but carry different color labels. A single Service in front of them selects on both labels — app=myapp and color=blue (or green). Nothing about the pods themselves changes during a cutover; only the Service's selector does. 

apiVersion: v1
kind: Service
metadata:
  name: myapp-svc
spec:
  type: ClusterIP
  selector:
    app: myapp
    color: blue   # change to green, then kubectl apply
  ports:
    - port: 80
      targetPort: 80

Verification is entirely observable through kubectl: kubectl get pods --show-labels confirms both colors are running, and kubectl get endpoints myapp-svc -o wide shows exactly which pod IPs the Service is currently sending traffic to. Flipping the selector back to blue and reapplying is the entire rollback procedure — no image rebuild, no redeploy.

Approach 2: Helm

Helm turns the same idea into a template. A single chart defines both a deploy-blue and a deploy-green resource, plus one Service whose selector reads an activeColor value from values.yaml: 

# values.yaml
activeColor: blue
image:
  repository: nginx
  tag: "1.25"
# templates/service.yaml
spec:
  selector:
    app.kubernetes.io/name: {{ include "diner.name" . }}
    color: {{ .Values.activeColor | quote }}

A cutover becomes one command: helm upgrade diner ./diner --set activeColor=green. Helm re-renders every template that depends on that value and reapplies only what changed. Because Helm keeps a release history, helm rollback diner 1 reverts to the previous revision — including its activeColor — without you having to remember what the old value was.

Approach 3: Terraform

Terraform expresses the same switch declaratively, as a single validated variable whose value flows into the resource graph: 

variable "active_color" {
  type        = string
  description = "Which color gets traffic: blue or green"
  default     = "blue"
  validation {
    condition     = contains(["blue", "green"], var.active_color)
    error_message = "active_color must be blue or green."
  }
}

An ingress.tf file resolves that variable to a concrete Service name through a locals lookup table, and the ingress backend references the resolved name: 

locals {
  service_map = {
    blue  = kubernetes_service_v1.blue.metadata[0].name
    green = kubernetes_service_v1.green.metadata[0].name
  }
  active_service_name = local.service_map[var.active_color]
}

Changing active_color in variables.tf and running terraform apply -auto-approve updates only the ingress backend reference — Terraform's plan output shows exactly that one change before it applies anything, and Terraform's state file becomes the permanent, auditable record of which color was live at any point in time.

A real debugging lesson from building this lab: the first version of ingress.tf tried to pick the active service with a ternary expression — var.active_color == "blue" ? kubernetes_service_v1.blue.metadata[0].name : kubernetes_service_v1.green.metadata[0].name — and it failed to parse cleanly in that provider version. The fix was to replace the ternary with the locals map lookup shown above: a map keyed by color is both easier to read and easier to extend if a third color is ever added, and pairing it with the variable's validation block means an invalid color is rejected at terraform plan time instead of producing a confusing runtime error. If you hit a similar parse error with conditional expressions in your own Terraform, a lookup map is usually the cleaner fix.

The tradeoff, across all three tools

None of the three approaches change the fundamental cost: a full standby environment has to be running and ready before you can trust it enough to flip traffic onto it. That is strictly more resource usage than a rolling update, which never runs two full copies at once. The payoff is that a bad release is undone by flipping a label, a value, or a variable back — not by re-running a deploy pipeline under pressure.

4. Lab

Lab objective: Stand up a blue and a green environment behind a single entry point three separate ways, cut traffic from blue to green, verify it, then roll back — once with raw manifests, once with a Helm chart, and once with Terraform.
1

Raw Kubernetes: apply blue and green Deployments plus a Service

Apply a manifest defining myapp (blue) and myapp-green (green) Deployments, each writing its own HTML banner to index.html at container start, plus a myapp-svc Service selecting on app=myapp, color=blue.

Predict before running: before you port-forward, write down which color's banner you expect to see. Run kubectl port-forward svc/myapp-svc 8080:80 and open http://localhost:8080 to confirm.

2

Raw Kubernetes: cut traffic to green, then roll back

Edit the Service's color selector to green and reapply. Refresh the browser — it should now show the green banner. Confirm with kubectl get endpoints myapp-svc -o wide: the listed pod IPs should now belong to the green pods, not blue.

Stop and think: what would you have to do differently if you instead wanted to roll back to blue? Then do it, and confirm it worked with the same endpoints command.

3

Helm: create and install the blue and green releases

Scaffold a chart with helm create diner, adjust the Deployment templates to add a color label and matching selector for each of blue and green, and template the Service's selector to read {{ .Values.activeColor }}. Install it with helm install diner ./diner, with activeColor: blue in values.yaml.

4

Helm: flip traffic and inspect the release history

Run helm upgrade diner ./diner --set activeColor=green. Confirm the switch with kubectl get pods --show-labels and by checking the Service's resolved selector. Then run helm history diner and read the revision list — note which revision is which activeColor before you decide whether to roll back.

5

Terraform: install, initialize, and validate

If terraform -version fails, install Terraform and make sure its directory is on your PATH before continuing — a missing binary is a common blocker and worth ruling out first. Run terraform init to download the Kubernetes and Helm providers declared in versions.tf, then terraform validate to confirm the configuration parses cleanly before you apply anything.

6

Terraform: apply with blue active, then verify

With active_color = "blue" in variables.tf, run terraform apply -auto-approve. Verify with kubectl get pods -n diner-lab --show-labels and kubectl describe ingress diner-ingress -n diner-lab — the ingress backend should list the blue Service.

7

Terraform: flip to green and confirm live routing

Predict before running: which Terraform resources do you expect to change when only active_color changes — all of them, or just the ingress? Change active_color to "green" and run terraform apply -auto-approve again. Read the plan output before confirming: it should show exactly one resource changing, the ingress backend.

Confirm with kubectl describe ingress diner-ingress -n diner-lab and a request against the ingress host. Then flip back to "blue" and reapply to prove the rollback path works too.

8. Post-Coding Quiz

Question 1 of 5

Why doesn't a blue-green rollback require rebuilding an image or rerunning a pipeline?

Blue-green keeps the previous environment fully intact and idle. Rollback is the same one-switch operation as the original cutover, just pointed the other direction.
Question 2 of 5

Why was the ternary expression in ingress.tf replaced with a locals map lookup?

The lookup map keyed by color, paired with the variable's validation block, replaced a parse failure with a construct that is both readable and safely extensible to a third color later.
Question 3 of 5

A rolling update is generally not a good substitute for blue-green when you need an instant rollback. Why?

Because a rolling update replaces pods gradually within one environment, at any given moment some pods are old and some are new — there's no clean single version to revert to instantly.
Question 4 of 5

What should be true about the green environment before you flip traffic to it in a real workflow?

Blue-green assumes the standby environment is already known-good before the switch. Session 12 builds the probes that make "known-good" something Kubernetes can verify automatically.
Question 5 of 5

Session 12 will focus on:

Session 12 covers the probes and HorizontalPodAutoscaler that keep pods provably healthy and appropriately sized — the missing piece behind "green is ready" and "there are enough pods."

9. Reflection Questions

  1. Which of the three approaches (raw kubectl, Helm, Terraform) felt like it would be safest to operate under pressure, and why?
  2. The lab's Terraform fix replaced a ternary with a locals map. Can you think of another place in infrastructure code where a lookup table beats a chain of conditionals?
  3. If your team could only afford to run blue-green for the highest-risk releases and rolling updates for everything else, how would you decide which category a given release falls into?

10. What Breaks If This Knowledge Is Missing?

  • No blue-green pattern, only rolling updates: every release risks a window where old and new versions serve traffic simultaneously, and a bad release requires a second rollout to undo instead of a single flip.
  • Flipping traffic without verifying the standby environment first: the switch works instantly, which also means a broken green environment goes live instantly — the value of blue-green depends entirely on verifying green before the flip, not after.
  • Ignoring the resource cost: teams that adopt blue-green everywhere without budgeting for double capacity are often the ones who quietly stop doing it under cost pressure, right when they need the safety net most.

11. What We Learned

Today you learned: blue-green deployment keeps two full environments running and switches all traffic between them atomically, and that idea can be implemented as a raw Service selector, a Helm value, or a validated Terraform variable resolved through a locals map — with the same instant-rollback property and the same double-resource tradeoff in all three.
